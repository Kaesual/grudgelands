# WP40 R8 production mapgen performance hardening

**Status:** the first focused re-review found one Medium selector fallback;
the explicit fail-closed correction is under replacement verification on
`wp40-r8-mapgen-performance`.

**Baseline:** `7e9284ffcd71b445efcdfde7cee39534bbf8ef35`.

## 1. Purpose and boundary

This is the bounded performance-hardening tranche of WP40 R8, not a new
top-level work package. R8 already owns production mapchunk timing and peak
RSS, and the first GUI world proved that the accepted writer generates stable
terrain but that fresh exploration remains visibly too slow.

The tranche may remove redundant computation, validation and evidence output
from the live runtime path. It must not change the selected seed, fixed
geometry, planner/content decisions, operation order, node content, `param2`,
light output, liquid scheduling, one-writer authority, or one-emerge-thread
setting. Offline evidence and capture constructors retain their fail-closed
checks.

The implementation stops for an explicit scope ruling if a proposed speed-up
requires changing any generated byte or accepted map semantic.

## 2. Measured baseline and hypotheses

The initial engine-free LuaJIT diagnostic measured one representative surface
owner at approximately 1.47 CPU seconds in planning and 2.66 CPU seconds in
the writer after a 4.15-second production construction. It observed about
8.5 million content-classification calls in production Lua after excluding
the fixture's Lua-only lighting simulation. These timings are diagnostic, not
release evidence.

Static tracing identified five bounded candidates:

1. runtime-discarded ledgers, canonical successor runs, checksums and P9G
   diagnostic sorting;
2. repeated deterministic `(x,z)` column evaluation in R5, R6 and P9G;
3. per-call `pcall`, type and purity validation around a content table already
   validated during construction;
4. duplicate R5 shadow-VM copying, classification and lighting preparation
   before R6 repeats the transaction work; and
5. retained full-volume buffers and a maximum-sized run buffer that increase
   resident memory and garbage-collector marking cost.

The live loader also constructs the full writer in the main Lua environment
although only zone authority is published there. The emerge environment owns
the sole live writer. Removing main-only writer allocation is a memory change,
not a generated-byte change.

An independent read-only Fable memory lens at the same baseline corrected the
retained production estimate to about 28.5 million array slots per full
construction: approximately 264 MB under LuaJIT or 507 MB under PUC 5.1 before
engine and transient memory. It independently ranked the duplicate main-state
construction, the R6 settlement/run buffers, the R5 adapter buffers, P8 digest
garbage, and the oversized R6 planner candidate scratch as the dominant
targets. It also explained the much larger fixture peak as offline capture/VM
material rather than a second hidden live writer. These findings support P1--P3;
owner-sized intent packing and R5/R6 buffer sharing remain deliberately outside
this tranche because they touch more accepted indexing and transaction code.

## 3. Fixed diagnostic corpus

Development measurements use seed `0` and these six existing R8 witnesses:

| ID | X | Y rule | Z | Purpose |
|---|---:|---:|---:|---|
| `human_capital` | 0 | surface | -1500 | dense authored surface/anchor |
| `goldmead_inland_housing` | 0 | surface | -2050 | ordinary inland surface |
| `wyrmglass_channel` | -2675 | surface | 0 | authored water/channel |
| `copperfell_shelf` | -2600 | surface | -2200 | coast/shelf surface |
| `deep_cross_border_resource` | -1691 | -842 | 191 | deep resource transaction |
| `capital_high_slice` | 0 | 240 | -1500 | vertically empty/native slice |

The harness records construction, planning and writer CPU time, canonical
content/`param2`/light digest, content-classification count, planner and
successor counters, Lua heap after full collection, and process peak RSS. It
runs the corpus in declared and reverse order in one process per order. These
two LuaJIT processes may run concurrently at idle priority and remain below
the workstation-wide seven-process cap.

Timing is advisory and compared by per-case median/category rather than used
as a fragile absolute gate. Exact output digest equality is mandatory.

## 4. Implementation sequence

### P0 -- measurement seam

Add one small engine-free performance runner around the authentic production
runtime fixture. Do not add per-voxel clocks or enable production log spam.
The committed runner is diagnostic tooling and defaults to LuaJIT.

### P1 -- low-risk runtime omissions

- In runtime mode, omit result-only ledgers, successor run materialization and
  checksums that do not influence settlement or map writes.
- Precompute decoration rule kinds instead of repeating `string.find` for
  every candidate column.
- Preserve all evidence, capture and ordinary fixture behavior.
- Avoid allocating the emerge-only writer buffers in the main environment by
  adding a construction mode limited to public zone/consumer authority.

### P2 -- bounded column reuse

Install one deterministic per-session memo at the `planner_source` seam. Its
key is the exact integer `(x,z)` coordinate and its value is the complete
immutable column tuple. Use a fixed-capacity or generation-bounded policy with
deterministic eviction; cache state must never affect returned values or
canonical iteration order. Reuse two-dimensional plans across vertical owners
only when the complete plan input is identical.

### P3 -- trusted runtime classification

Validate the registered CID classification table, tuple arity and purity once
during construction. Runtime-only settlement and adapter paths may then use a
direct trusted lookup. Evidence and capture constructors retain repeated
defensive classification. Unknown or invalid CIDs remain fail-closed under the
same policy as the accepted writer.

### P4 -- stop/go decision

Compare P0 with P1--P3. The tranche stops without a shadow-VM rewrite if the
six-case surface experience is materially improved, exact bytes remain equal,
and peak memory no longer threatens normal play. A twofold surface speed-up is
the engineering target, not an acceptance promise.

Only if the result remains visibly inadequate may the same branch proceed to
a direct R5-to-R6 projection seam that removes shadow-VM copying and redundant
R5 lighting work. That larger change requires a focused contract amendment and
review before implementation.

## 5. Verification and acceptance

- Every changed Lua file passes `tools/bin/luac51 -p`.
- Changed production Lua passes `SETGLOBAL` inspection and all five repository
  Lua sweeps. Tool Lua receives the same searches explicitly.
- Intermediate executable runs use LuaJIT only.
- The fixed diagnostic corpus produces byte-identical canonical output before
  and after every optimization stage, in both declared and reverse order.
- Existing targeted R7/R8 fixtures covering fresh halos, surface/deep light,
  liquids, successor settlement and runtime construction remain green.
- Frozen final production bytes receive exactly one compact PUC 5.1 run and
  the same micro-KAT once under LuaJIT, with byte-identical canonical output.
- One fresh independent Sol review checks the complete diff and immutable
  evidence; the reviewer does not repeat the PUC run.
- The user performs one short fresh-world GUI walk after merge, judging first
  join, nearby surface generation, sustained exploration and memory behavior.

No new full-layout, 32-seed, seven-worker or multi-hour engine fleet is part of
this tranche. Existing R6/R7/R8 evidence remains authoritative unless an exact
output comparison differs.

## 6. Candidate result and stop decision

The final post-fix LuaJIT measurement preserves every per-case content,
`param2` and light digest and the order-independent canonical digest
`d058a5bcd517348c67eb83b9957422d2c3e43cdbf000dcb4981ee6ca668a5dd4`.
The six-case planning-plus-writer CPU total fell from 18.137 to 2.991 seconds
forward and from 17.646 to 3.049 seconds in reverse order: 6.06x and 5.79x
speed-ups. End-to-end process wall time, including construction, VM fixture
work and output hashing, remained below nine seconds in both orders.

The review-recommended cache bound of 65,536 entries retains a complete
recent horizontal neighborhood. A surface plan followed by its high vertical
sibling recorded 121,744 cache hits and zero misses in each phase; the warm
high-slice plan took 0.031--0.034 seconds instead of the corpus's 0.278--0.282
seconds. The larger bound added approximately 13--15 MB to the fully populated
LuaJIT heap, a bounded trade for an 88--89% vertical-repeat planning reduction.

The main-state authority constructor and full emerge constructor publish the
same production manifest and anchor-roster hashes. In isolated construction
measurements, authority-only retained heap was 23,133,578 bytes versus
323,775,130 bytes for the full writer, a 92.9% reduction for the main-state
mapgen allocation. The full 61-case integration receipt is byte-identical to
the already tracked R8 projection receipt, and the dedicated Lua 5.1 static
gate passes.

The baseline timings remain advisory: their production commit and recorded
runner hash are bound, but the exact baseline wrapper bytes were not retained.
Peak RSS is therefore reported as a diagnostic only; retained Lua heap and the
isolated construction comparison are the accepted memory evidence.

This materially exceeds the P4 stop target. The riskier R5/R6 shadow-buffer
sharing, owner-sized intent indexing and packed intent representation are
therefore deferred. Exact rows and evidence hashes are recorded in
`wp40-r8-performance-result.tsv`.
