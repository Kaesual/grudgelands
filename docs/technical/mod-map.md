# Mod ownership map

Which mod owns which concern, the seams other mods call, and where the rules
live. Built on 2026-10-05 from the `mod.conf` files, the
`SETGLOBAL` listing and a count of `<global>.<name>` uses outside each mod.
The [module guide](module-guide.md) has the details per area (one file per area under `modules/`); the
[design docs](../design/README.md) own the game rules. Load order follows the
declared dependencies, a partial order: roughly BASE → `grug_sounds` →
`grug_core` → `grug_xp`, `grug_money` → ITEMS base → `grug_mapgen` →
`grug_factions` → `grug_classes`, `grug_visuals`, `grug_inventory`,
`grug_mobs` → feature mods. Two mods that do not depend on each other load in
an order the engine does not fix (`grug_mobs` names neither `grug_inventory`
nor `grug_classes`), and a CORE mod may load late (`grug_ambience` depends on
`grug_map`).

**Globals:** one table per mod, named after the mod, with two exceptions:
`grug_quality` publishes `grug_items` (the per-stack item model; the mod
sets no `grug_quality` table) and `grug_core` also publishes `grug_zones`
(the zone façade, `rawset` in `grug_core/zone_authority.lua`). The vendored
mobs_redo fork publishes `mobs`.

## Ownership traps

- **Two level APIs.** `grug_zones.mob_level_at` is the mapgen's level field;
  the level a mob gets on the surface is `grug_core.mob_level_at`, which
  asks the overlay `grug_mobs/spawn_regions.lua` registers through
  `grug_core.register_level_overlay` first.
- **`mod.conf` understates coupling.** These mods use another grug mod's
  global outside their declared `depends`/`optional_depends` closure, each at
  run time (in a function body or a mods-loaded callback, never at a file's
  top level), so none relies on load order: `grug_core` → `grug_gear`,
  `grug_inventory` (`give` in the 0.45.0 character step), `grug_jobs`,
  `grug_mail`, `grug_mapgen`, `grug_mobs`, `grug_quality`; `grug_nodes` and
  `grug_trees` → `grug_core`; `grug_gear` → `grug_core`, `grug_classes`,
  `grug_inventory`; `grug_xp` → `grug_classes`; `grug_money` →
  `grug_inventory` (`slot_order`); `grug_factions` → `grug_classes`,
  `grug_home`, `grug_inventory`, `grug_xp`; `grug_classes` →
  `grug_abilities`, `grug_gear` (`format_armor`), `grug_inventory`;
  `grug_visuals` → `grug_inventory`; `grug_housing` → `grug_inventory`;
  `grug_jobs` → `grug_quality` (`grug_items`); `grug_mobs` → `grug_home`,
  `grug_inventory`, `grug_mounts`, `grug_quests`; `grug_traders` →
  `grug_guild`, `grug_repair`; and the vendored `default` calls
  `grug_inventory.give`. (A sweep of `<global>.` and `<global>[` uses per
  mod against the transitive `mod.conf` closure, comment text dropped,
  2026-11-17; a use built from a computed name escapes it.) A fixture that
  loads one mod alone needs stand-ins for what it calls.
- **"compatibility" and "legacy" in a name do not mean removable.** The zone
  authority's compatibility adapters are the live `grug_zones` API, and
  `grug_mobs.registered_cadence` is the live mob registry.
- **mobs_redo is a fork,** not an upstream tree: read the vendored
  `mods/ENTITIES/mobs/api.lua` and VENDOR.md, not upstream documentation.
