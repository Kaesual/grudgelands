# W2 — Mapgen wp13: capital and town layouts

- Finder model: claude-opus-5-5
- Files read in full: 7 of 42 (`highcourt.lua`, `highcourt_plot.lua`, `hearthpine.lua`, `highcourt_districts.lua`, `highcourt_district_martial.lua`, `kezamba_lagoon.lua`, `kezamba_lots.lua`). The other five `*_plot.lua` and three `*_districts.lua` were compared in full, code line by code line (comments stripped), against Highcourt's. Partly read: `kezamba.lua:1-550`, `nhal_veyr.lua:600-900`, and the helper and stamp sections of `dawnmere`, `kapok`, `silverleaf`, `stillgrave` and `sunscar.lua`. Skimmed through function-body hashes and diffs, as the brief allows for authored data: the remaining 25 district roster files (including `lethariel_districts.lua` and `kezamba_districts.lua`) and the data parts of `dur_brannoc.lua`, `gor_drazhak.lua`, `lethariel.lua` and `nhal_veyr.lua`. Not reached: none.
- Summary: The package is pure, load-time composition code. I found no per-chunk work, no unseeded randomness, no `x ^ 2` and no order-dependent `pairs` in output (determinism is clean). Duplication is the real issue, and X2-05 understated it: the six capital plot modules share 78-95 % of their CODE line for line with `highcourt_plot.lua` (220-269 of ~280 lines each; about 1,250 redundant code lines). What they really differ in fits in about 15 parameters. The comments are re-worded rather than copied, which is why the raw diff gave only 60 %. The district files, by contrast, are mostly authored data: only 14 of 161 `decorate` closures are duplicated. Their shareable part is the wrapper. Several copies have drifted: Kezamba's rosters ask for `garden = true` on four plots, but its builder has no garden branch (W2-02); Hearthpine still skips props silently, the Dawnmere-only and Kapok-only prop guards were never spread (W2-03); and the airspace rule differs between capitals (W2-05). No file in the package is in the preparation-authority digest, so an output-identical refactor is compatible (see "Good to know").

### W2-02 | Medium | dup | Kezamba's rosters ask for `garden = true` on four plots; its plot builder has no garden branch, so the flag does nothing

- **Where:** `mods/MAPGEN/grug_mapgen/wp13/kezamba_districts.lua:246`, `:354`, `:452`, `:532` (`margin = 4, garden = true`); `kezamba_plot.lua:125-370` (`M.build`, with no `plot.garden` read anywhere). Gor Drazhak's builder also lacks the branch, but no Gor Drazhak roster sets the flag.
- **What:** The four well-court rows (`shore_well` and the three others, template `highcourt_well_court`) were copied with Highcourt's `garden = true` and a `margin = 4`. In Highcourt that margin is "the ring its wider ground bought" for four fruit trees, two planters, a bench and crates (`highcourt_plot.lua:275-289`). Kezamba's builder never had the branch (`git log -S "plot.garden"` shows no Kezamba commit; `git show 6f166da00:…/kezamba_plot.lua` has no `garden`). Kezamba's four well courts therefore stand on four nodes of bare ground, and the roster says otherwise. Nothing fails, so no fixture could notice.
- **Evidence:** `rg -n "garden\s*=\s*true" kezamba_districts.lua` returns the 4 rows; `rg -n "garden" kezamba_plot.lua` returns only the comment at `:131`.
- **Proposal:** Decide which way it should go.
  - (a) Remove the four flags, which documents the current world. This is a byte change only, so it is compatible.
  - (b) Give the engine (W2-01) a troll `garden` spec, for example `jungle_tree` with planters, and plant the four courts. This changes the cells, so it is a map reset; schedule it with the next capital output change.

  In both cases, add a guard to the engine: a roster key the engine does not know is an error, so the next copied flag fails loudly.
- **Effort:** S · **Risk:** low (a), medium (b) · **Upgrade class (guess):** compatible (a) / map reset (b)
- **Confidence:** high

### W2-03 | Medium | dup | The prop guard exists in six drifted versions; Hearthpine still drops props silently, and the socket-cell and indoors rules live in one town each

- **Where:**
  - `mods/MAPGEN/grug_mapgen/wp13/hearthpine.lua:176-192`: `paved_prop` and `prop` `return false` and every caller ignores the result (`:253-328`).
  - `dawnmere.lua:227-277`: refuse, plus a socket-cell rule (`socket_cells`, "Round 36 review: the west end bench stood on the green's west guard waypoint's front cell").
  - `kapok.lua:235-292`: `open_air` with an indoors rule and a prop height.
  - `sunscar.lua:294-350`: `obstruction()` names the blocker.
  - The basic version is in `silverleaf.lua:232-255`, `stillgrave.lua:258-296`, `highcourt.lua:343-373`, `dur_brannoc.lua:279-308` and `lethariel.lua:347-379`.
  - `nhal_veyr`, `gor_drazhak` and `kezamba` have `paved_prop` only.
- **What:** Every file after Hearthpine states the rule "Every prop the composition asks for MUST land; a prop quietly skipped is a hole…" (`highcourt.lua:340-342`, `sunscar.lua:288-292`, the "Dawnmere lesson"). Hearthpine, the oldest start, never got it: a fence, kerb, pile, crate, planter or bench that does not fit simply vanishes. The two later safety rules were also added to one composition each and never spread. Dawnmere's "no prop on a socket's cell" exists because a bench once stood on a waypoint. Kapok's "no prop on a cell inside a plot footprint" exists because a cleared room passed the emptiness test. The other nine compositions can still put a prop on a socket's standing cell, or inside a stilt house's cleared floor, without any error.
- **Evidence:** The function-body hashes of `prop` differ across the files listed (2bc216 Hearthpine, 8382a2 Dawnmere, bcbbe8 Kapok, 8c0ab1 Sunscar, 547695 for the four basic ones, 762133 Highcourt). Hearthpine has no `refuse` (`rg -c 'local function refuse' hearthpine.lua` returns nothing).
- **Proposal:** Move one guard set into `layout.lua`: `layout.props(buf, opts)`, which returns `prop`, `paved_prop` and `place`. It refuses with Sunscar's message and has optional `socket_cells` and `outdoors` checks plus a `height`. Use it in all 12 compositions. Run the twelve compositions offline FIRST: a guard that fires would make a world fail to load. If none fires, the output is byte-identical (a guard only raises; it never writes). If one fires, that is a real hole, and fixing it changes the cells (map reset).
- **Effort:** M · **Risk:** medium (a load-time error if an existing prop violates a new rule) · **Upgrade class (guess):** compatible if no guard fires, otherwise map reset
- **Confidence:** medium (it is certain that the guards differ; whether Hearthpine or any other composition drops or misplaces a prop today needs an offline build)

## Good to know

- **Upgrade class of a byte change in this package:**
  - None of the 42 files is in the preparation-authority default list. `wp40/preparation_identity.lua:9-19` names only `../wp13/city_edge.lua` and `../wp13/plot_approach.lua` from wp13.
  - The world-folder layout cache digests the whole mapgen tree (`wp40/layout_cache.lua:45-71`), so a byte change costs one cache rebuild at the next boot, not a start failure.
  - The preparation identity also hashes the generated layout texts (`wp40/r7_runtime.lua:334-343`, `:548-553`), and the capital layout depends on each plot's `bounds` and `clear_to` (`wp40/capital_planner.lua:2598`, `wp40/r7_capitals.lua:157`).
  - So: byte-identical output is compatible. Any change to a plot's bounds or `clear_to` produces a new capital layout, which makes a full-preparation world fail its next start; the class is "map reset". A cell change that keeps bounds and `clear_to` still changes the manifest's blueprint identity; also treat it as a map reset.
  - Moving a per-capital table INTO `wp40/r7_capital_blueprint.lua` (digested) would make even an output-identical refactor fail full-preparation worlds. Keep new modules in wp13.
- **When things run:** everything in this package runs at load or lazy-build time, never per mapchunk. Kits and plots are prepared once per Lua environment (`wp40/world_assembly.lua:90`, `:96-107`). After `IDLE_RELEASE = 64` idle plans a lazy settlement drops its cells and rebuilds through the same `M.build`/`M.core` (`wp40/r7_settlement.lua:131-134`, `:1436-1452`, `metrics.build_calls`). Build cost therefore recurs when players move back and forth across capitals. That is wp40's policy; `metrics.build_calls` is the probe to watch.
- **Determinism is clean:** the only `pairs` loops copy `extra` fields into a fresh table (order-free). There is no `math.random`, no `^`, and the hashes use integer `%` and `math.floor`. Palette lists sort with `parts.less_bytes`.
- **Safety net for W2-01 and W2-04:** the lazy rebuild already fails loudly if a rebuilt blueprint's identity, landmarks, `reference` or `clear_to` differ from the published ones (`wp40/r7_settlement.lua:1440-1451`). The same comparison, run offline on several seeds, is the byte-identity proof a refactor needs.
- **Nhal Veyr's standing-position reservation** (`nhal_veyr.lua:650-675`) is a third way of keeping scatter off sockets, next to Highcourt's paved loop corners (`highcourt.lua:132-135`) and `gate_watch.clear_cover`. If W2-03's shared guard is built, this reservation is the model for a `socket_cells` option.
