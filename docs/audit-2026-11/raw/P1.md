# P1 — World map, character visuals, displays, quickbar

- Finder model: claude-opus-5-5
- Files read in full: 35 of 36; skimmed: `mods/PLAYER/grug_map/icon_masks.lua` (generated tooltip masks, structure and key list only); not reached: none
- Summary: The package is in good shape on its hot paths. The minimap sends only `hud_change` diffs and rebuilds its cell texture about every 13 nodes. The map window refreshes on events, with a per-pass budget. The location sampler, head look and wield poll are all throttled. HUD ids are recreated on every join, and no relog defect was found. The most valuable items are: the unbounded `grug_visuals` compose cache, which every NPC look seed grows (P1-01); the 1 s wield poll, which does more per player than its comment and the design doc state (P1-02); and the per-entity `on_step` orphan check on every wield entity (P1-03). Some dead leftovers can go: the unreachable "Back to inventory" branch, the baked-icon pipeline (which still drives the base cache key) and an unused public wrapper. Several technical docs and file headers still describe the Round 44 to 47 map (baked minimap icons, a 2 s `page.lua` poll), so they need a docs pass. The engine submodule `reference_projects/luanti` is not checked out here, so every engine claim below is marked "engine behaviour not checked".

## Findings

### P1-01 | Medium | perf | The compose cache in `grug_visuals` grows without bound, one entry for each NPC look seed

- **Where:** `mods/PLAYER/grug_visuals/compose.lua:304-307`, `:487-516`, `:555-565`; NPC look seeds `mods/PLAYER/grug_visuals/looks.lua:302-309`; callers `mods/ENTITIES/grug_mobs/guard.lua:172-180`, `bandit.lua:101`, `bosses.lua:662/891/931`
- **What:** `grug_visuals.compose` stores every result in `cache[key]` forever. Only `index_armor` at load ever clears it. The key contains the full look string (`look_string(look)`), race, bracket, armour pieces with broken flag and enchant pair, zone colours and offhand. Every NPC rolls its own `_grug_look_seed` (MINSTD over the 3 to 5 options of 5 categories, several hundred looks per race), so each distinct guard or bandit look × race × bracket adds a new entry. That entry holds a skin string of roughly 0.5 to 1.2 KB, the atlas string, a `textures` table and a digest. Players add one entry for every gear, enchant or broken-state combination they ever wear. Over a long uptime with NPCs activating and deactivating all over the world, the table only grows.
- **Evidence:** `cache[key] = result` (`compose.lua:564`). The only clear is the loop in `index_armor` (`:205-207`), called once from `apply.lua:943` at `register_on_mods_loaded`. `rg -n "grug_visuals.cache" mods` finds nothing else. Upper bound: 6 races × (4·6·4·3·3 = 864 human looks, similar for the others) × 6 brackets × royal/armour-colour variants, so tens of thousands of possible keys.
- **Proposal:** Cap the cache, for example with a two-generation table: when `count >= N` (say 2048), move `cache` to `old` and start a new `cache`; a hit in `old` is promoted. Repeat calls must still return the identical table, so the `apply.lua` key compares and `apply_entity`'s `_grug_visual_key` digest compare stay valid. An evicted key is simply recomposed. Keep `grug_visuals.cache` pointing at the live table, or give `index_armor` a `clear()` function.
- **Effort:** S · **Risk:** low · **Upgrade class (guess):** compatible
- **Measure:** unmeasured. On a larger machine, seed 42, run a server for 2 to 4 h with a player stand-in touring the start towns and outposts. Every 10 minutes, log the entry count of `grug_visuals.cache` and the summed `#skin + #armor` bytes, then compare against the capped version.
- **Confidence:** medium (the growth is certain; its size in MB depends on how many NPC activations a real server sees)

### P1-02 | Low | perf | The 1 s wield poll rebuilds a visual ItemStack and re-derives pose and scale for every player, every second

- **Where:** `mods/PLAYER/grug_visuals/apply.lua:721-739` (poll), `:143-189` (`sync_wield`), `:88-104` (`wield_appearance`), `:528-542` (`shown_item`); claim in `:711-717`, `wield_geometry.lua:293-295`, `docs/design/character_visuals.md:362`
- **What:** The poll's comment says the per-player work is "one `get_wielded_item`, one group lookup and one string compare". `sync_wield` actually runs on every poll and does the following before it compares anything:
  - `wield_appearance(stack)`: a new `ItemStack(name)`, two `get_meta`, six `get_string`/`set_string` pairs and `to_string()`.
  - for a non-empty hand, `pose_for` (up to nine `core.get_item_group` calls).
  - `stack:get_meta():get_string("wield_image")` and `wield_item_scale`.

  The compare against `_grug_wield_appearance` comes only after all of this. With 100 players that is about 100 visual stacks and a few thousand engine calls per second that change nothing. `wield_geometry.lua`'s comment, that the poll "allocates nothing", is also wrong.
- **Evidence:** `apply.lua:146` `local appearance = stack and grug_visuals.wield_appearance(stack) or nil` and `:160-164` both run unconditionally on every call. The poll calls `sync_wield(entry, player, shown, entry.stature)` for every connected player (`:727-733`).
- **Proposal:**
  - Cache pose and scale per item name in a small table. `pose_for` depends only on the name and its registered groups. `wield_item_scale` depends on the definition plus the stack's `wield_image` meta, so cache the definition part and read `wield_image` once.
  - Read the six appearance meta fields straight from the wielded stack's meta, and build the visual stack only when they or the name differ from the last poll. Keep a cheap signature string on the entry.

  What must stay identical: the entity gets the same `textures`, `wield_item`, pose and scale, and a failed spawn still retries on the next poll.
- **Effort:** S · **Risk:** low · **Upgrade class (guess):** compatible
- **Measure:** unmeasured. With 50 to 100 player stand-ins idle at a start town, measure the globalstep time of the poll (`core.get_us_time()` around the loop) over 5 minutes, before and after.
- **Confidence:** high

### P1-03 | Low | perf | Every wield entity runs a Lua `on_step` on every server step, only to notice an orphan

- **Where:** `mods/PLAYER/grug_visuals/apply.lua:38-74`
- **What:** Each armed NPC and each player carries one `grug_visuals:wield` entity. Its `on_step` adds dtime and returns until one second has passed. Each active wield entity therefore costs an engine-to-Lua call on every server step, about 11 per second. Hundreds of armed guards, bandits and vendors in loaded areas add up to hundreds of Lua calls per step that do nothing. The orphan case it guards is a parent removed without removing its child, which in practice means a mob that dies or is removed.
- **Evidence:** `on_step = function(self, dtime) self._grug_age = self._grug_age + dtime; if self._grug_age < ORPHAN_CHECK then return end ...` (`:64-73`). `rg "_grug_wield_obj" mods` outside `grug_visuals` finds no removal at mob death or removal; the orphan check is the only cleanup. Engine behaviour not checked (does the engine skip the Lua call for an entity without `on_step`?).
- **Proposal:** Remove the wield entity explicitly where the parent goes: the `grug_mobs` register wrapper's `on_die` / `on_deactivate`, and `grug_traders` vendors. Then either drop `on_step` or keep one shared, throttled sweep: a single globalstep every 1 s that walks a weak set of the wield entities and removes the unattached ones. Unloads need no handling, because `static_save = false` already removes the entity with its block.
- **Effort:** M · **Risk:** medium (a missed removal path leaves floating swords) · **Upgrade class (guess):** compatible
- **Measure:** unmeasured. Seed 42, stand at a capital with about 200 active armed NPCs, and compare the server step time (`--profiler` or the `luaentity_Step` share) before and after.
- **Confidence:** medium

## Good to know

- Refresh design: the map window's sends are event-driven and budgeted at 8 checks and 2 builds per 0.1 s pass. world_map.md measures about 18 KB per send and up to about 1.1 MB per minute for one viewer in a walking party (Round 67). This is accepted, not a finding.
- Minimap: every element remembers what was last sent, and only whole-pixel diffs go out. The cell texture (up to 4 base tiles, plus 4 flight tiles and 4 claim tiles, plus mask) is rebuilt about every 13 nodes. Clients never free these textures; world_map.md "Cells" documents and measures this.
- HUD bookkeeping: grug_quickbar and grug_displays own no HUD at all. The minimap, side elements, location banner and head-look override are created per join and their state is dropped on leave, so ids cannot leak across a relog.
- Character visuals: the texture list is written only when compose's key, the cloak, the wings or the Scout's back card change. `visual_size` is rewritten on every apply on purpose (mobs_redo resets it on dismount). The stored appearance JSON is written only when it differs.
- `grug_displays` keeps state only in node metadata. Projection entities are unsaved and rebuilt by an LBM that runs at every load. Puts, takes and moves check `grug_core.interaction_protected`.
- `grug_keys` reads `get_player_control_bits` for every player on every step, unthrottled on purpose (a key edge lasts one step).
- `reference_projects/luanti` is not checked out in this checkout. Every engine claim above is unverified against the engine source.
