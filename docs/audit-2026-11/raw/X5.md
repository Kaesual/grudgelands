# X5 — Persistence and upgrade safety (cross-cutting)

- Finder model: claude-fable-5-2
- Files read in full: 4 of n/a (`grug_core/migrations.lua`, `world_version.lua`, `map_reset.lua`, `grug_mobs/map_reset.lua`; plus `docs/technical/upgrade-contract.md`); skimmed: every other store was read at its persistence sites only (found by `rg` for `get_mod_storage`, `set_string/set_int`, `core.deserialize`, `get_staticdata`, `safe_file_write`, `create_detached_inventory`, `register_on_leaveplayer/on_shutdown`), about 45 files in `mods/PLAYER`, `mods/ENTITIES/grug_mobs`, `mods/ITEMS/grug_repair`, `mods/MAPGEN/grug_mapgen`; not reached: item-meta formats in `grug_quality`/`grug_gear`/`grug_abilities` beyond their deserialize sites, node meta of `grug_farming`/`grug_signs`/`grug_smelting`, vendored `BASE` node meta, unknown node names read from the map, the tolerance of every held-item definition lookup written since Round 41.
- Summary: The saved state is in good shape: the guard, the runner and the map reset are consistent, every mod-storage user loads after `grug_core`, every map-bound mod-storage key has its clear, no player meta holds a position, and almost every reader tolerates an unreadable or unknown value. No Critical or High item was found. The most valuable items: one player-bound item store (`grug_mobs:pending_boss_loot`) and the job's `target` stack are missing from the contract's removed-item list, so a future step that follows the list misses them (X5-01); a relog wipes all ability cooldowns and refills mana while other cooldowns were persisted on purpose against exactly that (X5-02); `grug_parties` is the one store that stops the server start on a bad record (X5-03). The contract's own tables lag behind the code since 0.70.0 (X5-06). Engine behaviour was not checked: `reference_projects/luanti` is not checked out in this worktree.

## Findings

### X5-01 | Medium | persist | Two player-bound item stores are outside the contract's removed-item list and outside every step

- **Where:** `mods/ENTITIES/grug_mobs/bosses.lua:147-201` (player meta `grug_mobs:pending_boss_loot`); `mods/PLAYER/grug_jobs/operation_jobs.lua:179,202,224` (`target` in player meta `grug_jobs:job` / `grug_jobs:queue`); `docs/technical/upgrade-contract.md:50` (§1 row "A removed item"), `:525` (step 0.47.0: "no other player-bound storage holds items")
- **What:** Boss loot that did not fit is kept as a `core.serialize`d list of item strings in player meta and handed out at the next join. An enchant or upgrade job keeps the gear stack it works on as an item string (`target`) in the job record. Neither store is named in the contract's list of what a removed or transformed item must cover (inventories, `recovered:*`, `packed:*`, mail), and no step file reads them; step 0.67.0 covers the job's `consumed` only. A future step written from §1 leaves the item as an unknown-item stack in these stores, or leaves gear there unconverted.
- **Evidence:** `bosses.lua:159-161` `pending[#pending + 1] = leftover:to_string()` / `meta:set_string(pending_key(), core.serialize(pending))`, read back at `:188-200`; the key exists since commit `4c1380003` (2026-09-18), before release mode. `rg -n "pending_boss_loot" tools/migration docs/technical docs/process AGENTS.md` finds nothing. `tools/migration/steps/v0_67_0.py:133-138` reads `record["consumed"]` only; `rg -n "target" tools/migration/steps/v0_67_0.py` finds nothing.
- **Proposal:** Add both stores to the §1 row and to §5.8's "every store a removed item covers", and correct the 0.47.0 sentence in a note (the pushed step stays). Optionally give the data API one helper that walks every player-bound item store, so a step cannot forget one. No game code changes.
- **Effort:** S · **Risk:** low · **Upgrade class (guess):** compatible
- **Confidence:** high

### X5-02 | Medium | edge | A relog clears every ability cooldown and refills mana

- **Where:** `mods/PLAYER/grug_abilities/init.lua:3087-3099` (leave), `:3052-3053` (join)
- **What:** Ability cooldowns, mana and rage live only in memory. Leaving drops them, joining sets mana to the maximum, so a reconnect outside PvP gives full mana and every skill ready, the 300 s Sprint and the 60 s skills included. The potion cooldown, the trinket cooldowns and the talent windows' internal cooldowns are kept across a relog on purpose, for this reason.
- **Evidence:** `init.lua:3093` `cooldowns[name] = nil`, `:3091` `mana[name] = nil`; `:3053` `refill_mana(player)` in the join callback; `scout.lua:334` `cooldown = 300`. Contrast `mods/ENTITIES/grug_traders/potion.lua:27-30` ("relogging to chain-chug potions is exactly the exploit the shared cooldown exists to prevent"), `mods/PLAYER/grug_trinkets/init.lua:112-114`, `mods/PLAYER/grug_classes/talent_windows.lua:11-12` ("The ICD outlives death, respec and a relog within the same server run"). Only a flagged PvP logout is punished (`grug_pvp/init.lua:422-425`). No design document states that a relog resets cooldowns (`rg -i "relog|reconnect|logout" docs/design` has no cooldown or mana hit).
- **Proposal:** Keep `cooldowns[name]` and the mana value in memory by name across a leave within one server run (as the talent windows do), or store an expiry per skill above some length in player meta as the potion cooldown does. A server restart may still reset them. Ask the user first: it may be intended.
- **Effort:** S · **Risk:** low · **Upgrade class (guess):** compatible
- **Confidence:** medium (the behaviour is certain; whether it is wanted is not)

### X5-03 | Low | persist | grug_parties refuses the server start on any stored party it does not accept

- **Where:** `mods/PLAYER/grug_parties/init.lua:3-30`
- **What:** The one `parties` key is deserialized and checked with `assert`s at mod load. A stored group the checks reject stops the load, so the server stays down until somebody edits the mod storage by hand; a later change of a party rule (the size limit, a new required field) turns every stored party into a start refusal that needs a declared step. Every other store drops a bad record; `grug_clans`, the same shape, was written that way.
- **Evidence:** `init.lua:4-6` (`core.deserialize(saved)` then `assert(type(state) == "table" ...)`), `:15-29` (asserts per group, e.g. `#group.members <= 10`, `"Missing stored leader"`). Compare `mods/PLAYER/grug_clans/init.lua:26-35` (keeps the text as `clans_unreadable`, starts empty) and `:54-88` (drops a bad clan or member with a warning).
- **Proposal:** Validate as `grug_clans` does: drop an invalid group with a warning, keep an unreadable text under a second key, start empty. Valid stored parties must load exactly as now.
- **Effort:** S · **Risk:** low · **Upgrade class (guess):** compatible
- **Confidence:** high

### X5-04 | Low | perf | grug_clans serializes every clan at each member's join and leave

- **Where:** `mods/PLAYER/grug_clans/init.lua:91-93,517-540`
- **What:** All clans live in one mod-storage key. Each join and each leave of any clan member stamps `last_online` and rewrites the whole table (`core.serialize` of every clan with up to 100 member rows each). The cost per login grows with the number of characters that ever joined a clan, not with the clan concerned.
- **Evidence:** `:91-93` `storage:set_string("clans", core.serialize(state))`; called from the join callback (`:522`) and the leave callback (`:539`), which run once per member login and logout; a member row holds name, role, level, class, last_online (`:8-13`).
- **Proposal:** One key per clan (`clan:<id>`) plus `next_id`, written only for the clan that changed; the old single key read once and split is a format change of non-map-bound state, so it needs a declared step, or keep the single key and write the presence stamp only at leave and shutdown (halves the writes with no format change).
- **Effort:** S (the stamp) / M (the split) · **Risk:** low · **Upgrade class (guess):** compatible (the stamp) / migrate (the split)
- **Measure:** unmeasured; time `persist()` with 20 clans of 100 members on the larger machine, and count calls over a 100-player login wave.
- **Confidence:** medium

### X5-05 | Low | perf | The quest state grows with every completed quest and is rewritten whole on each credited kill

- **Where:** `mods/PLAYER/grug_quests/state.lua:13-16,41-47,668-686,726-740`
- **What:** `grug_quests:state` is one `core.serialize`d table that keeps every completed quest id forever. Each kill or use that credits an objective copies the whole table (`table.copy`) and serializes it again, the completed set included. The game ships about 550 quests, so a late character rewrites a string of several kilobytes per credited kill.
- **Evidence:** `:13-14` "`completed` keeps the completion forever"; `:41-42` `editable` = `table.copy`; `:44-46` `core.serialize(state)` then `set_string`; `Q.credit_kill` `:679-686` and `Q.credit_use` `:734-740` call both per credited event. `rg -c '"objectives"' mods/PLAYER/grug_quests/data/zones` sums to 551.
- **Proposal:** Keep `completed` under its own meta key (written only at a turn-in) and the active progress under another; that is a format change of character state, so a declared step with a join part, or a new key that the code fills and the old one stays readable only through the step. Decide only after measuring.
- **Effort:** M · **Risk:** medium · **Upgrade class (guess):** migrate
- **Measure:** unmeasured; a character with 400 completed quests and one active kill quest, time `Q.credit_kill` over 1000 kills before and after.
- **Confidence:** medium

- **Checked and in order:** every mod-storage user depends on `grug_core` (`mod.conf`), so the guard runs before any of them; no `BASE` mod opens mod storage or a world file (`beds` spawns were removed by a GRUG PATCH). Every `map_reset.clear` runs before its owner's first read (`grug_housing` reads first on purpose and clears the loaded registry). No player meta holds a position (`rg pos_to_string|string_to_pos` has log lines only). The camp rewrite records nothing when a reset is pending (`camp_rewrite.lua:185`). Writes on change only: `grug_pvp` location (`:268-274`), `grug_jobs/state.lua:9-16`, the camp markers (`camps.lua:503`). No per-tick mod-storage or player-meta write was found; the densest are `liveness.watch` (one small int per watched rare or dragon per 10 s pass while it is missing) and the guild effect's save loop.
- **Shutdown:** the mods that must save at a leave also save in `register_on_shutdown` (`grug_pvp/init.lua:433`, `grug_mounts/entity.lua:1035`, `restore.lua:208`, `grug_clans/init.lua:546`); `grug_guild/effect.lua:429-435` saves on a timer instead. The assumption behind them (the engine saves the players before it kicks them, leave callbacks may not run) is stated in `grug_pvp/init.lua:431` and `grug_clans/init.lua:543-545`; engine behaviour not checked.
- **Readers that accept an older format for good** (no step retires them, so they must stay): `grug_pvp:logout_death` value `"1"` (`grug_pvp/init.lua:51-53`), a job without `delivered` (`grug_jobs/jobs.lua:40,794`), a quest entry without `variant` (`grug_quests/state.lua:120`), a favourite stored as a recipe id (`grug_jobs/ui.lua:234-247`), a character without `grug_jobs:held` (`basic_unlock.lua:14-17`) or without `grug_map:visited_zones` (`zone_discovery.lua:19`). The baseline rule (contract §5.2) forbids a later step from relying on any of them having run.
- **Item-meta copies of definition data** are the place where an upgraded world differs from a fresh one: `tool_capabilities`, `_grug_repair_caps`, `grug_ilvl`, `description`. Steps 0.45.0 and 0.47.0 exist because of them. A change to a tool's or weapon's definition numbers needs the same treatment again (`grug_items.refresh_capabilities`), in every store of X5-01 too.
