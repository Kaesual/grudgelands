# M4 — Mapgen wp40: R7, capitals, POI blueprints

- Finder model: claude-fable-5-2
- Files read in full: 37 of 54; skimmed: `city_decor_catalog.lua` (generated data: structure, row counts and constant fields checked with rg), `r31_pvp_poi_blueprint.lua` lines 110-270 (the fortress cell authoring; head and tail read), 15 of the 18 nine-line `r7_*_{village,outpost,bandit_camp}_blueprint.lua` wrappers (three read, all 18 compared mechanically: they differ only in the schema/race/kind line); not reached: none
- Summary: The package is correct and deterministic where it matters: the capital planner runs only in main, both environments build from the deserialized text, every output sort has a total comparator, no `x ^ 2` and no unseeded randomness were found. No Critical or High item. The valuable items are per-chunk waste in the R7 successor tail (all 144 settlements build a race palette and closures on every chunk transaction; the P9G scan reads each column 12 to 24 times), and a per-boot cost the world-folder cache does not cover yet (main rebuilds and hashes every blueprint on a cache hit although emerge already runs from the handover of exactly that data). Around that sits a layer of hand-over leftovers: 18 identical wrapper files, evidence modes nobody calls, dead manifest rows, and many copies of the same small helpers. Two design docs state turret spacings the code overrides. All proposals except the two marked "published digest moves" keep generation output byte-identical.

## Findings

### M4-01 | Medium | perf | Every chunk transaction builds a race palette, closures and a ledger for all 144 settlements

- **Where:** `mods/MAPGEN/grug_mapgen/wp40/r7_settlement.lua:1581-1766` (`tail.settle`, notably 1597-1633 and 1763-1765), called for every roster row by `mods/MAPGEN/grug_mapgen/wp40/r7_successor.lua:127-129`; the palette constructor `mods/MAPGEN/grug_mapgen/wp13/palette.lua:981-1028`
- **What:** `settle` does its setup before it knows whether the settlement touches the chunk: a footprint string from four numbers (1597), `approach_palettes.new(profile.race)` (1620), five role lookups (1621-1624), two closures (1603, 1625) and a result table (1763). `palette.new` walks about 115 roles and, for each role of the race, scans the required and optional lists linearly (`contains`, palette.lua:954, 1018-1021). The roster has 144 rows (6 starts, 6 capitals, 18 R14, 70 R20, 18 PvP, 26 camps), and at most one or two are near any chunk.
- **Evidence:** `r7_successor.lua:127` `for index = 1, #settlements do ledger[settlements[index].key] = settlements[index]:settle(context) end`; `r7_settlement.lua:1620` `local fit_palette = approach_palettes.new(profile.race)` is unconditional; the only consumers of `fit_palette`, `fit_write` and `reach` sit under `collar_work` (1634) and `state.active` (1676, 1703). Keep the write order (collars, cells in blueprint order, edge) and the `write_span` rule as they are. Output byte-identical.
- **Effort:** S · **Risk:** low · **Upgrade class (guess):** compatible
- **Measure:** unmeasured; emerge time per chunk transaction far from any settlement, before/after, same seed and area (the Round 49 probe area), plus one capital chunk column to confirm identical node hashes.
- **Confidence:** high

### M4-02 | Medium | perf | P9G scan reads every column once per catalogue row, twice when it is land

- **What:** On a column-cache miss the scan runs 12 catalogue rows x 25 cells x 256 columns and calls `context.column_values_at(x, z)` per row and column for `surface_y` (566), then again inside `geographic_reason` (314) for water class, zone and biome. All four values are row-independent.
- **Evidence:** loop `for catalog_index = 1, cached and 0 or #rows` (557) around the cell and column loops (559-567); `context.column_values_at` forwards to `planner_source.column_values_at` (`r6_settlement.lua:3234-3236`), a cached query that normalizes x/z and returns 20 values (`zones.lua:1576-1592`). - **Confidence:** medium

### M4-03 | Medium | perf | Main rebuilds and hashes every blueprint on each boot although the layout cache hit

- **Where:** `mods/MAPGEN/grug_mapgen/wp40/r7_runtime.lua:258-298` (the `prepare` loop, 276-277), `mods/MAPGEN/grug_mapgen/wp40/world_assembly.lua:220-221`, `mods/MAPGEN/grug_mapgen/wp40/r7_loader.lua:94-119` and `:133`
- **What:** The world-folder cache stores the four layout texts only. Emerge skips exactly this work by taking main's `prepared_blueprints` handover, which is plain data and a pure function of the seed, the capital layout text and the mapgen source files, i.e. of the cache key.
- **Evidence:** `world_assembly.lua:220` `W.capital_plots = texts.capital == nil and variant.protection == nil and A.capital_plots() or {}`; `r7_runtime.lua:276` `r7_settlement_module.prepare(profile, source, raw_sha256, prepared_handover or capital_plots)`; `r7_settlement.lua:952-968` builds whenever the cache has no entry; `r7_loader.lua:133` builds the handover and `:387` ships it to emerge; the hit line at `:452-458` logs this remaining time as "runtime construction".
- **Proposal:** store `prepared_blueprints` as a fifth section of the layout cache (same key, same "any failure rebuilds" rule) and hand it to `r7_runtime` in main on a hit, as emerge receives it; relax the "emerge hands nothing over" guard (`r7_runtime.lua:656`). Emerge's check of every lazy rebuild against the identity (`r7_settlement.lua:1443-1455`) stays the safety net. Side effect to keep in mind: main also holds the six starts' cell tables for the whole run although no writer exists there (`r7_settlement.lua:899` drops only lazy cells; `preparation_source.lua` reads none). Output byte-identical.
- **Effort:** M · **Risk:** medium · **Upgrade class (guess):** compatible
- **Measure:** unmeasured; the "runtime construction %.1f s" figure of the cache-hit log line before/after on the same world, and the manifest sha256 unchanged.
