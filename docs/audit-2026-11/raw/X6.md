# X6 — Security and exploits (cross-mod)

- Finder model: claude-opus-5-5
- Files read in full: cross-cutting package without a file list; every handler site found by `rg` was read at its handler and at the functions it calls (listed in "Good to know"); skimmed: `grug_traders/prices.lua` (sell price only), `grug_pvp/init.lua` (gate and header only), `grug_mobs/start_villagers.lua` (NPC right-click dispatch only), `grug_parties/init.lua`, `grug_clans/init.lua` (API entry points only); not reached: economy balance (buy/sell arbitrage between vendor price tables, left to the traders finder), `grug_abilities` per-ability target filters beyond the central `deal_ability_damage` gate.
- Summary: The security posture of the value flows is good and consistent: every vendor, repair, crown, mail, mount, quest, lift, waystone, housing and expedition handler keeps a server-side session, re-validates range, faction and entitlement at submit time, recomputes prices and offers from the catalogue and cross-checks the shown snapshot, and moves money and items through `grug_money.take_with_inventory` or an equivalent expected-stack check; detached inventories all check the actor name, and every `register_allow_player_inventory_action` callback that returns a number does so only for its own list (OR short-circuit contract honoured). The one realistic exploit found is a denial of service: two handlers run Lua's `trim` (`^%s*(.-)%s*$`, quadratic in a run of inner blanks) on a raw, uncut formspec field, which the project itself already guards against elsewhere; the withdraw dialog is open to every player (X6-01). The rest are small edges. The engine submodule `reference_projects/luanti` is not checked out, so every engine claim below is marked "engine behaviour not checked".

## Findings

### X6-01 | High | security | Quadratic trim on an uncut formspec field lets any player stall the server

- **Where:** `mods/PLAYER/grug_money/coins.lua:62-73` (called from the withdraw handler `coins.lua:230-247`); `mods/PLAYER/grug_housing/stone_form.lua:649-653` (`target_name`, called from `set_access` on the stone form's Interact/Everything/Remove buttons, `stone_form.lua:786-791`)
- **What:** `grug_money.parse_amount` runs `tostring(row[1] or ""):trim()` on the three raw Gold/Silver/Copper field values, and the Claim Stone form runs `(fields.perm_name or ""):trim()`, both before any length cut. `string.trim` is `^%s*(.-)%s*$`; on a value like `"x" .. (" "):rep(n) .. "y"` the lazy `(.-)` retries the greedy `%s*$` at every position, so the cost grows with n². A modified client that submits one withdraw packet with a field of a few hundred kilobytes holds the server step for seconds, and can repeat it. The withdraw dialog is reachable by every player (Inventory page button `grug_inventory/pages.lua:678`, `707-709`), so no level, claim or privilege is needed; the stone form needs a Claim Stone owner. The withdraw re-show also echoes the whole field back into the formspec (`coins.lua:208-210`), and the stone form keeps the raw value in `session.typed` (`stone_form.lua:758`).
- **Evidence:** The project already documents this exact vector and cuts first elsewhere: `grug_jobs/ui.lua:740-747` ("a client may send a field of hundreds of kilobytes, and the trim's pattern takes time that grows with the square of the spaces in it") and `grug_inventory/help.lua:422-427` ("cut first: a client may send a huge field"); `grug_mail/model.lua:67-79` (`M.truncate` reads only `4 * max` bytes) for the same reason. `rg -n ":trim\(\)" mods` outside BASE finds exactly these two field sites plus chat-command params (see Backlog). Field values arrive as long strings from the client (engine behaviour not checked; the claim rests on the project's own comment in `grug_jobs/ui.lua:741-743`).
- **Proposal:** Cut before trimming, as `grug_jobs._clean_field` does: in `parse_amount` use `tostring(row[1] or ""):sub(1, 32)` (a whole number of copper never needs more) before `:trim()`; in `target_name` cut `fields.perm_name` to the player-name limit (e.g. `:sub(1, 4 * 20)`) before `:trim()`, and store the cut value in `session.typed`. Better still, route both through the existing `grug_jobs._clean_field`-style helper (or a shared `grug_core` one, since `help.lua` carries a copy) so the rule lives once. Accepted inputs stay identical.
- **Effort:** S · **Risk:** low · **Upgrade class (guess):** compatible
- **Confidence:** high (pattern cost), medium (that the engine forwards a field that large)

### X6-02 | Low | edge | A displayed item can be taken from inside a claim by digging its support outside the claim

- **Where:** `mods/PLAYER/grug_displays/nodes.lua:118-122` (`preserve_wall_item`), `:131-147` (frames), `:203-217` (weapon holder)
- **What:** Item frames and the weapon holder are `attached_node = 2`. Taking the shown item is guarded by the claim's interaction permission (`allow_take` → `interaction_refused`) and digging by `can_dig` (protection plus empty), but the comment at `:118-119` notes that losing the support bypasses `can_dig`, and `preserve_wall_item` then drops the displayed stack as a free item entity. Placement is judged only at the frame's own node, so a frame inside an active claim mounted on a wall node that lies outside the claim (a house wall on the claim edge, or a frame hung from the inside onto terrain past the boundary) can be emptied by any player who digs that outside node and picks the item up.
- **Evidence:** `nodes.lua:29-33` (`can_dig` = protection + empty), `:90-93` (take guarded), `:116-122` and `:212` (`preserve_metadata` returns the stack as a drop). `core.is_protected` decides the support node by its own position (`grug_housing/protection.lua:42-48`, `model.protects(pos, ...)`). Builtin's attached-node drop calling `preserve_metadata` is engine behaviour not checked (the code comment asserts it).
- **Proposal:** Either refuse `on_place` of a display whose support node is not protected for the placer the same way as the display position (the support must be in the same claim when the display is), or, in `preserve_wall_item`, keep the shown stack only when the node's position is not inside an active claim and otherwise hand it to the claim's recovered belongings / drop nothing. The first keeps all current behaviour outside claims.
- **Effort:** S · **Risk:** low · **Upgrade class (guess):** compatible
- **Confidence:** medium

### X6-03 | Low | edge | The profession trainer's submit re-checks only the distance to the open-time position

- **Where:** `mods/PLAYER/grug_jobs/trainers.lua:186-202`
- **What:** Unlike every other NPC service (mounts `trainer.lua:23-44`, innkeeper `innkeeper.lua:2-11`, repair provider `providers.lua:17-42`, quests `npc.lua:338-342`), `valid_session` checks only that the player is within 8 nodes of the position stored at open; it does not re-check that the trainer entity is still the live socket NPC, the player's faction or that the player is alive. Learning and unlearning cost nothing today, so nothing can be gained; it is a drift from the shared "re-validate at submit" pattern that would turn into a hole the day learning gets a price or a requirement.
- **Evidence:** `trainers.lua:186-193` (distance only), `:168-185` (open stores `entity` but the handler never validates it except for the repair button, which goes through `grug_repair`'s own provider check).
- **Proposal:** Reuse `grug_repair`'s trainer provider check (`grug_repair.can_open_trainer(player, session.entity)`, which already validates entity, socket, faction and distance) or an equivalent `permitted()` in `valid_session`. Behaviour for legitimate clicks stays identical.
- **Effort:** S · **Risk:** low · **Upgrade class (guess):** compatible
- **Confidence:** high

## Backlog notes

- Chat-command params run the same unbounded trim (`grug_clans/init.lua:499`, `grug_parties/init.lua:463`, `grug_money/init.lua:188`, `grug_ambience/rules.lua:43`); harmless as long as the engine's `chat_message_max_size` (default 500) is enforced before the chat hook, which I recall it is (engine behaviour not checked); a server that sets it to 0 reopens X6-01's cost through `/c` and `/p`.
- `grug_bridge/link.lua:206-217` `Link.ledger` keeps every command id the website ever sent for the process lifetime (no pruning); bounded only by restarts.
- Leaving the game clears combat at once (`grug_core/combat.lua:605-620`, `:664`); a relog escapes a PvE fight (the 30-minute Return home cooldown and the persisted PvP contact still hold, `grug_home/travel.lua:216`, `grug_pvp/init.lua:72-89`).
- Respawn lock (`grug_expeditions/respawn_lock.lua`) relies on the death screen formspec; whether an old client's legacy respawn packet still respawns directly was not checked (engine behaviour not checked).
- A faction player's swing on a factionless player keeps engine damage without any PvP flag (`grug_abilities/init.lua:2860-2867`); only reachable against a character still in creation stasis.
- `grug_guild/vendor.lua:56-62` and `grug_guild/stonewright.lua:146-154` log and lose an item if `give` returns a rest after `fits` passed (documented as unreachable; `grug_mail/api.lua:247-255` and `grug_bridge/commands.lua:251` drop it at the player's feet instead — one rule would be nicer).
- `grug_accounts/flow.lua:146-153`, `:221-227`: the 5-attempts-per-10-minutes link limit is session state and resets on relog; documented in `docs/technical/web-accounts.md:139-141` and backed by the website's own limit, 32^10 code space.
- `/faction <name>` (`grug_factions/init.lua:366-397`) shows any online player's faction to anyone (information only).
