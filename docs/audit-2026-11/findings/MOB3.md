# MOB3 — grug_mobs bosses, rift and species (verified)

- Finder model: claude-opus-5-5
- Verifier model: claude-opus-5-5
- Files read in full: 58 of 58 (the boss, dragon, arena, floor, depth pulse, rift and golem files line by line; the species files' code lines in full); skimmed: the long comment blocks of the 51 species files (read where a finding cites them); not reached: none
- Summary: The boss layer is in good shape: one ledger and lockout path (`settle_boss`) for kings, dragons, the rift boss and Expedition credit, one reset outcome (`reset_home`) for every boss rule, a bounded flood fill for the boss floor, and the dragon fight state is runtime-only and cleared on every exit. The real defects are small: a dragon whelp's kill gives no death grace although the design counts "another encounter NPC", an enraged dragon rewrites its properties every server step, and the rift's particles bypass the one particle path (spawners longer than 1 s go to every player, and `grug_particle_scale = 0` does not switch them off). The largest cleanup is in the species files: 37 surface `mobs:spawn` rows (about 530 code lines) are retired at load and never run, which also silently removed the Elder Bear and Silverback rolls the design still describes; and 823 of the 3,081 code lines in the 51 species files consist only of default-valued fields that a family helper with archetype defaults would supply.
- Verifier note: engine behaviour checked in `reference_projects/luanti` (5.18.0, `e8f12bf`). `set_properties` with unchanged values sends nothing (MOB3-02 corrected to Low); an unattached spawner with `time > 1` does go to every connected player (MOB3-03 holds, but at a pulse every 14 s it is Low). The "trap" for MOB3-04 does not apply: `mobs.spawning_mobs[name]` is filled by `mobs:register_mob` (`mods/ENTITIES/mobs/api.lua:4122`), not by the spawn rows.

## Findings

### MOB3-01 | Medium | bug | A dragon whelp's kill gives no 60 s death grace; whelp hits never enter the loot ledger

- **Verdict:** CONFIRMED — `encounter_death` (`bosses.lua:114-127`) accepts only `_grug_boss_id` or `_grug_royal_summon`; whelps get `_grug_boss_summon` (`boss_dragons.lua:674`), which `bosses.lua` never reads; the hit hook (`bosses.lua:96-98`) also checks `_grug_boss_id` only. `docs/design/world.md:803-807` names "another encounter NPC" as a grace-giving killer for dragons.
- **Where:** `mods/ENTITIES/grug_mobs/bosses.lua:96-98`, `:114-127`; `mods/ENTITIES/grug_mobs/boss_dragons.lua:674` (`_grug_boss_summon`)
- **What:** `encounter_death` counts a player's death for the death grace only if the killer entity has `_grug_boss_id` or `_grug_royal_summon`. Dragon whelps carry `_grug_boss_summon` instead, so a ledger participant killed by a whelp is not eligible after respawning. `docs/design/world.md:803-806` says a participant "slain during the active attempt by the encounter, another encounter NPC or an enemy player" keeps eligibility for 60 s. Also, the hit hook (`bosses.lua:96-98`) adds a player to the ledger only for a mob with `_grug_boss_id`, so damage to whelps (which joins the *fight* in `boss_dragons.lua:1121-1128`) never enters the *loot* ledger. For kings, damage to a royal guard counts (the guards set `_grug_boss_id`, `bosses.lua:809`).
- **Evidence:** `bosses.lua:125-126` `return ent and (ent._grug_boss_id or ent._grug_royal_summon) ~= nil`; `boss_dragons.lua:674` `ent._grug_boss_summon = self._grug_boss_id`; `rg "_grug_boss_summon" mods` finds no read in `bosses.lua`.
- **Proposal:** In `encounter_death` (and, if the design wants it, in the `register_on_player_hit_mob` hook) also accept `ent._grug_boss_summon`, mapping it to that boss id. Kings, Generals and the rift boss stay as they are.
- **Effort:** S · **Risk:** low · **Upgrade class (guess):** compatible
- **Confidence:** high (the death grace); medium (whether whelp damage should give loot participation: world.md only says "the same participation bounds as a royal encounter")

### MOB3-02 | Low | perf | An enraged dragon calls `set_properties({glow = 8})` on every server step

- **Verdict:** CORRECTED — the per-step call is real (`boss_dragons.lua:988`), but the network claim is wrong: `ObjectRef::l_set_properties` (`reference_projects/luanti/src/script/lua_api/l_object.cpp:1026-1031`) compares the new properties with the old ones and calls `notifyObjectPropertiesModified` only when they differ, so an unchanged glow sends nothing. What remains is one Lua table, a full `ObjectProperties` copy and a compare per step for at most two dragons. Medium → Low.
- **Where:** `mods/ENTITIES/grug_mobs/boss_dragons.lua:988`
- **What:** `dragon_tick` runs on every step of the dragon (`do_custom`). Once the dragon is enraged (below 50 % HP, for the rest of the fight), it allocates a table and calls `set_properties` on every step. The engine copies and compares the whole property set each time but sends no message while the glow is already 8. The glow was already set once in `enrage` (`:688`).
- **Evidence:** `if self._grug_enraged then self.object:set_properties({glow = 8}) end` sits unconditionally in the per-step path. The only other writers are `enrage` (`:688`) and `cancel_dragon_action` (`:795`). The likely reason for the per-step write is re-applying the glow after a reactivation, since `_grug_enraged` survives in staticdata. Engine: `l_object.cpp:1026-1031`.
- **Proposal:** Apply the glow once in the dragon's `after_activate` when `self._grug_enraged` is set (`:1186-1189`), or keep a runtime flag (`self.temp.grug_glow_set`) and write only when it is missing. The look stays the same.
- **Effort:** S · **Risk:** low · **Upgrade class (guess):** compatible
- **Measure:** none needed; the cost is a small per-step CPU item.
- **Confidence:** high

### MOB3-03 | Low | perf | The rift's particles bypass the one particle path: spawners over 1 s reach every player and ignore `grug_particle_scale`

- **Verdict:** CORRECTED — the engine rule holds: `Server::SendAddParticleSpawner` (`reference_projects/luanti/src/server.cpp:1736-1765`) applies the distance check only to unattached spawners with `0 < time <= 1`; any other spawner without `playername` goes to every client. Server-side a spawner with no player costs only an id (`server.cpp:3760-3776`). But the two public spawners run once per void pulse (every 14 s of a rift-boss fight, `rift.lua:323`) and once per boss rise (`:412`): two small packets per player per 14 s on the one rift. Medium → Low. Also, `grug_particle_scale` is a server setting (`grug_core/particles.lua:98`), not a per-player choice.
- **Where:** `mods/ENTITIES/grug_mobs/rift.lua:177-195` (`emit_particles`), `:235-245` (`pulse_particles`), callers `:297`, `:323`, `:412`
- **What:** `rift.lua` is the only file in the package that calls `core.add_particlespawner` directly; every other effect goes through `grug_core.particles.play`. The header of `mods/CORE/grug_core/particles.lua:7-12` records the reason for that path: an unattached spawner with `time` above 1 s "goes to every player on the server", so the helper clamps `time` to (0, 1]. The rift's pulse wind-up spawner lives 2 s (`PULSE_WINDUP`) and its arrival burst lives 1.5 s, both without `playername`, so each one is serialized to every connected player. Neither the pulse spawners nor the crack's 5 s private spawners are scaled by the server's `grug_particle_scale`, so a server that set it to 0 still sends them. The crack's `exptime` of up to 4 s is also above the helper's `MAX_EXPTIME = 3`.
- **Evidence:** `rift.lua:236-243` `core.add_particlespawner({amount = amount, time = time, ...})` with `time = PULSE_WINDUP (2)` at `:323` and `1.5` at `:412`. `particles.lua:79` `MAX_TIME = 1`, `:98` `particles.SCALE`, `:380-382` (`SCALE <= 0` returns). `rg "add_particlespawner" mods/ENTITIES/grug_mobs` finds only rift.lua. Engine: `server.cpp:1736-1765`.
- **Proposal:** Move the three rift effects into `grug_core/particle_effects.lua` (for example `rift_pulse_windup`, `rift_pulse`, `rift_rise`, `rift_crack`) and play them through `grug_core.particles.play`, splitting the 2 s wind-up into 1 s pieces as `warn_dragon` does (`bosses.lua:1037-1040`). For the crack, either play it as a public 1 s effect each period or have the helper accept a `playername`. The counts can stay as they are.
- **Effort:** S · **Risk:** low · **Upgrade class (guess):** compatible
- **Measure:** not needed for the decision; the packet count follows from the pulse interval.
- **Confidence:** high

### MOB3-04 | Medium | dead | 37 surface spawn rows (about 530 code lines) are retired at load; with them the Elder Bear and Silverback rolls and four spawn checks never run

- **Verdict:** CONFIRMED — load path: `mobs:spawn` → `spawn_specific` (`mobs/api.lua:4469-4506`, sets `spawning_mobs[name].aoc`) → `mobs.register_spawn_abm` (`:4670`), replaced by `spawn_abms.lua:63-72`, which drops every row `grug_mobs.spawn_row_kept` (`spawn_policy.lua:939-951`) refuses; all 38 `mods/ENTITIES/grug_mobs/data/zones/*.spawns.json` have a `recipe` and a `critters` key and `SR.install_zone` stores the parsed recipe (`spawn_regions.lua:226-256`); boot logs record the retirement (`tools/r49_jit/evidence/boot1/server.log`: "56 surface spawn rows retired", an older count over the whole mod). `elder_roll`/`silverback_roll` are only the rows' `on_spawn`, which mobs_redo calls only from the row's `spawn_action` (`mobs/api.lua:4646`); `subtypes.lua:575-579` mentions them as if live. `_grug_spawn_check` runs only through `mobs:spawn_abm_check` (`init.lua:373-383`), i.e. from the ABM path. The trap does not apply: `mobs.spawning_mobs[name]` is created by `mobs:register_mob` (`mobs/api.lua:4122`), so deleting the rows keeps every `add_mob` working; only `.aoc` would go, and every `add_mob` caller passes `ignore_count = true` (`spawn_regions.lua:794,1031,1241`, `camps.lua:414`, `depth_pulse.lua:321`, `rares.lua:186-190`, `grug_traders/vendors.lua:749-750`, the breed path `mobs/api.lua:1637-1639`); the spawner node (`mobs/spawner.lua:115,192`) tests only existence.
- **Where:** surface `mobs:spawn` rows in `bear.lua:123,165`, `boar.lua:137`, `boar_variants.lua:84,119`, `bog_ooze.lua:90`, `bog_witch.lua:66`, `carrion_crow.lua:116`, `crocodile.lua:128`, `eagle.lua:127,148`, `golem.lua:217,226,244`, `hyena.lua:78`, `jungle_ape.lua:107`, `jungle_lynx.lua:89`, `panther.lua:84`, `ram.lua:79`, `serpent.lua:82`, `shore_crab.lua:73,76`, `skeleton_archer.lua:151,174`, `skeleton_raider.lua:166`, `speargrass_tiger.lua:40`, `spider.lua:95,127,164`, `stag.lua:99,120`, `war_construct.lua:30`, `wolf.lua:82,104`, `zebra.lua:77`, `zombie.lua:86,129` (all `mods/ENTITIES/grug_mobs/`)
- **What:** `spawn_abms.lua:68-72` drops every row for which `grug_mobs.spawn_row_kept` (`spawn_policy.lua:939-951`) is false. That function keeps underground rows, the five water authorities and the Rift Spawn row; it keeps a surface row only for a zone without a recipe or for a zone critter. All 38 `data/zones/*.spawns.json` carry a recipe with a `critters` list (rabbit, hare, gull, parrot, bone_weevil, bog_fowl, wild_turkey, song_bird; some lists are empty), and `biomes_mobs.md` §4 says "every zone has one since Round 28". So the 37 rows above register no ABM. They still record a chance and an aoc in `mobs.spawning_mobs`, but every runtime spawner calls `add_mob` with `ignore_count = true`. Three things are lost with these rows:
  (a) `bear.lua`'s `elder_roll` and `jungle_ape.lua`'s `silverback_roll` run only as these rows' `on_spawn`, and the spawn regions spawn sub-types with authored tiers (`subtypes.lua:575-579`). So the "Elder ... rolled 1 in 10 at spawn" of `biomes_mobs.md:769` and `:813` never happens.
  (b) The `_grug_spawn_check` functions of `shore_crab.lua:14-21` (`near_water`, a 13³ `find_nodes_in_area`), `speargrass_tiger.lua:3-6` and `skeleton_archer.lua:47-59` run only from these ABM rows. The spawn regions never call them (`rg "_grug_spawn_check|spawn_allowed" spawn_regions.lua camps.lua subtypes.lua` finds nothing).
  (c) The rows' long budget comments (for example `bone_weevil.lua:100-116`, `golem.lua:174-208`) describe ABM budgets that no longer apply.
- **Evidence:** I classified each row by `max_height` and name against the keep rules (25 rows are kept: the underground rows, the water rows, the critters and Rift Spawn). Block sizes are counted from `mobs:spawn({` to `})`. `rg -c critters data/zones/*.json` gives 38 of 38. Verifier: the exact count of 37 was not recounted.
- **Proposal:** Decide with the design owner. Either (1) delete the retired surface rows and their checks and rolls, keep a single list of the "palette fallback" families if the no-recipe path must stay alive, and update `biomes_mobs.md` §3.1 (Elder and Silverback) and the comment at `subtypes.lua:575-577`; or (2) if the Elder and Silverback should still exist, move the roll to the base def's `after_activate` (as `subtypes.lua` does for zone variants), so it does not depend on an ABM row. The kept rows (critters, underground, water, Rift Spawn) must stay byte-identical, so `spawn_abms.lua`'s merged chances do not move. Deleting a row is safe for `add_mob` (see verdict); a server-side `<mob> = chance,aoc` override in the config would then no longer be logged for that mob.
- **Effort:** M · **Risk:** low · **Upgrade class (guess):** compatible
- **Confidence:** high (retired at load); medium (that no zone without a recipe can appear at runtime: `SR.zone_ids()` comes from the loaded zone records)

### MOB3-05 | Medium | simplify | The species files are 27 % default-valued boilerplate; a family helper with archetype rows would replace about 1,000 lines

- **Verdict:** CONFIRMED — spot counts agree in size (`rg -l` over the whole package, which includes non-species files: `light_damage = 0` in 57 files, `visual = "mesh"` in 58, `stepheight = 1.1` in 45; the finder's per-field numbers are over the 51 species files only); `hyena.lua:8` carries the "byte-identical to wolf.lua's" guard. The saving estimate was not recounted. The "defaults" are the project's common values, not all mobs_redo defaults, so the archetype tables must state them explicitly; `grug_mobs.register_mob` copies the def into `base_defs` (`init.lua:702`) for sub-types, so a helper must hand it the same complete table.
- **Where:** the 51 species files in the package (`zombie.lua` … `lava_flan.lua`, `golem.lua`); 5,736 lines: 3,081 code, 2,213 comment, 442 blank
- **What:** Every species file writes a full mobs_redo definition by hand. Counted over the code lines (comments stripped), **823 of 3,081 lines consist only of fields at their common default** (`water_damage = 0`, `lava_damage = 4`, `light_damage = 0`, `visual = "mesh"`, `visual_size = {x = 1, y = 1}`, `jump = true`, `jump_height = 4`, `stepheight = 1.1`, `fear_height = 6`, `pathfinding = 1`, `attack_players = true`, `reach = 3`, `run_velocity = 4.6`, `attack_type = "dogfight"`, the critter quartet `passive/runaway/_grug_tier = "critter"/run_velocity = 3.4`, and the spawn-row `interval = 20`, `min_height = 0`, `max_height = 600`, `min_light = 10`/`max_light = 5`+`day_toggle = false`). Per field: `light_damage = 0` 49 files, `visual = "mesh"` 50, `water_damage = 0` and `lava_damage = 4` 44 each, `stepheight = 1.1` 39, `pathfinding = 1` 37, `jump = true` 34, `attack_players = true` 33, `reach = 3` 31, `run_velocity = 4.6` 29, `fear_height = 6` 26, `visual_size = {x = 1, y = 1}` 26. On top of that, mesh-bound blocks are copied verbatim: the Dungeon Master mesh's animation and selection box (`dungeon_master.lua:27-36`, `land_guard.lua:15-23`, `rift.lua:334-375`), the skeleton mesh's box, selection and animation (`skeleton_archer.lua:111-124`, `skeleton_raider.lua:72-85`, `bog_witch.lua` the same box with drifted clip speeds), the panther mesh (`panther.lua`, `jungle_lynx.lua`: the same box, selection and animation), the cave crawler mesh (`cave_crawler.lua:45-57`, `bone_weevil.lua:59-69`), the gull mesh (`gull.lua`, `carrion_crow.lua`). Drop tables are copied with comments that guard against drift instead of a shared value (`hyena.lua:7-8` "byte-identical to wolf.lua's — do not 'improve' one without the other"; the boar table in `boar.lua:75-79` and `boar_variants.lua:59-63`), although `biomes_mobs.md` §3.2 names the pairs as binding tables. Repeated comment boilerplate adds about 200 lines (`Rotated selection box = measured mesh bounds` 35×, `Mesh scale rule (boar.lua)` 26×, `T10 cliff rule` 16×, `engine-owned` 26×).
- **Evidence:** the counts above are from `rg -c` over the 51 files and an awk pass that marks a code line as removable when every `key = value` on it is in the default set.
- **Proposal:** `grug_mobs.register_family(name, row)` in one helper file with archetype tables (`melee`, `ranged` = melee plus `dogshoot`, the arrow override, view 16 and run 4.0, `critter`, `prey` = `passive_prey`, `swimmer`, `flier`), a `MESHES` table (mesh, base box, selection, animation, atlas count per model) and a `DROPS` table keyed by the §3.2 table names. A species then becomes a data row such as `{base = "melee", mesh = "hyena", voice = "canine", clock = "any", min_level = 10, walk = 1.5, view = 14, drops = "wolf", verb = "pack_hunter"}` plus only its deviations. Comments that justify a deviation stay with the row; reasons that hold for all rows move to the helper once. Estimate: about 820 default lines plus about 150 lines of copied mesh and drop blocks go, about 1,000 of the 3,081 code lines, plus about 200 comment lines; with MOB3-04's retired rows, about 1,500. Must stay identical: every registered entity's resulting definition table. A one-off check can dump `core.registered_entities[name]` for all names before and after.
- **Effort:** L · **Risk:** medium (many registrations; mobs_redo's field whitelist and `register_mob`'s wrappers must see the same tables) · **Upgrade class (guess):** compatible
- **Confidence:** high (the counts); medium (the size of the saving)
