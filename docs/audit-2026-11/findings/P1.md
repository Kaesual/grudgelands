# P1 — World map, character visuals, displays, quickbar (verified)

- Finder model: claude-opus-5-5
- Verifier model: claude-opus-5-5
- Files read in full: 35 of 36; skimmed: `mods/PLAYER/grug_map/icon_masks.lua` (generated tooltip masks, structure and key list only); not reached: none
- Summary: The package is in good shape on its hot paths. The minimap sends only `hud_change` diffs and rebuilds its cell texture about every 13 nodes. The map window refreshes on events, with a per-pass budget. The location sampler, head look and wield poll are all throttled. HUD ids are recreated on every join, and no relog defect was found. The most valuable items are: the uncapped `grug_visuals` compose cache, which grows with every new NPC look combination (P1-01); the 1 s wield poll, which does more per player than its comment and the design doc state (P1-02); and the per-entity `on_step` orphan check on every wield entity (P1-03). Some dead leftovers can go: the unreachable "Back to inventory" branch, the baked-icon pipeline (which still drives the base cache key) and an unused public wrapper. Several technical docs and file headers still describe the Round 44 to 47 map, so they need a docs pass. Engine claims were checked by the verifier against `reference_projects/luanti` where noted.

## Findings

### P1-01 | Medium | perf | The compose cache in `grug_visuals` is never trimmed and fills with every new NPC look combination

- **Verdict:** CORRECTED — the cache is indeed never trimmed (`compose.lua:304-307`, `cache[key] = result` at `:564`; only `index_armor`, `:204-206`, clears it). But the key holds `look_string(look)`, not the seed (`:492-494`), so entries grow per distinct (race, look, armour line/bracket, royal, zones, weapon, offhand) combination, not per seed: the cache is bounded by that key space and approaches it as new NPCs keep rolling random seeds (`looks.lua:302-309`). Title and "What" corrected; severity kept Medium as a cheap, clear memory cap.
- **Where:** `mods/PLAYER/grug_visuals/compose.lua:304-307`, `:487-516`, `:555-565`; NPC look seeds `mods/PLAYER/grug_visuals/looks.lua:283-309`; NPC callers `mods/ENTITIES/grug_mobs/guard.lua:172-180`, `bandit.lua:101-107`, `bosses.lua:892`, `start_villagers.lua:524-525`, `mods/ENTITIES/grug_traders/vendors.lua:230`
- **What:** `grug_visuals.compose` stores every result in `cache[key]` for the life of the server; only `index_armor` at load clears it. The key covers race, skin, the full look string, royal, NPC line default, zone colours, each armour piece (line, bracket, broken flag, enchant pair, layers), weapon and offhand. Each new NPC rolls a random `_grug_look_seed` (MINSTD over the five look categories), so as mobs spawn and despawn over a long uptime the set of distinct looks per race × NPC kind × bracket fills up (guards and bandits wear their line at the bracket their level buys, so up to six brackets each). The finder's estimate of several hundred looks per race gives an upper bound in the tens of thousands of entries; each holds a skin string of roughly 0.5–1.2 KB, the armour atlas string, the key, a `textures` table and a digest, so the worst case is tens of MB. Players add one entry per gear, enchant or broken-state combination they ever wear. The size actually reached depends on NPC turnover and is unmeasured.
- **Evidence:** `cache[key] = result` (`compose.lua:564`); key built at `:492-516`; the only clear is `index_armor` (`:204-206`), called once from `apply.lua:943` at `register_on_mods_loaded`. Callers compare results by `result.key` (`apply.lua:617`, `:648`) and `result.digest` (`apply.lua:917-918`), i.e. by string, never by table identity across calls, so an evicted entry that is recomposed is equivalent.
- **Proposal:** cap the cache, for example with a two-generation table: when `count >= N` (say 2048), move `cache` to `old` and start a new `cache`; a hit in `old` is promoted. Keep `grug_visuals.cache` pointing at the live table (`index_armor` iterates it), or give `index_armor` a `clear()` function. `apply.lua:622` treats the result as read-only, which an eviction does not change.
- **Effort:** S · **Risk:** low · **Upgrade class (guess):** compatible
- **Measure:** unmeasured. Run a server for 2 to 4 h with a player stand-in touring start towns and outposts; every 10 minutes log the entry count of `grug_visuals.cache` and the summed `#skin + #armor` bytes, then compare against the capped version.
- **Confidence:** high (no trimming); medium (size reached in practice)

### P1-02 | Low | perf | The 1 s wield poll rebuilds a visual ItemStack and re-derives pose and scale for every player, every second

- **Verdict:** CONFIRMED — `apply.lua:146` computes `wield_appearance(stack)` (new `ItemStack`, six meta copies, `to_string`, `:88-104`) and `:160-164` compute pose and scale before the compare at `:180`, for every connected player each second (`:721-739`); the comment at `:711-717` claims only one read, one group lookup and one compare. The cost is small in absolute terms (Low is right).
- **Where:** `mods/PLAYER/grug_visuals/apply.lua:721-739` (poll), `:143-189` (`sync_wield`), `:88-104` (`wield_appearance`), `:528-542` (`shown_item`); claim in `:711-717`, `wield_geometry.lua:293-295`, `docs/design/character_visuals.md:362`
- **What:** The poll's comment says the per-player work is "one `get_wielded_item`, one group lookup and one string compare". `sync_wield` actually runs on every poll and does the following before it compares anything:
  - `wield_appearance(stack)`: a new `ItemStack(name)`, two `get_meta`, six `get_string`/`set_string` pairs and `to_string()`.
  - for a non-empty hand, `pose_for` (up to nine `core.get_item_group` calls).
  - `stack:get_meta():get_string("wield_image")` and `wield_item_scale`.

  The compare against `_grug_wield_appearance` comes only after all of this. With 100 players that is about 100 visual stacks and a few thousand engine calls per second that change nothing. `wield_geometry.lua`'s comment, that the poll "allocates nothing", is also wrong.
- **Evidence:** `apply.lua:146` `local appearance = stack and grug_visuals.wield_appearance(stack) or nil` and `:160-164` both run unconditionally on every call. The poll calls `sync_wield(entry, player, shown, entry.stature)` for every connected player (`:727-733`).
- **Proposal:**
  - Cache pose and scale per item name in a small table. `pose_for` depends only on the name and its registered groups. `wield_item_scale` depends on the definition plus the stack's `wield_image` meta, so cache the definition part and read `wield_image` once.
  - Read the six appearance meta fields straight from the wielded stack's meta, and build the visual stack only when they or the name differ from the last poll. Keep a cheap signature string on the entry.

  What must stay identical: the entity gets the same `textures`, `wield_item`, pose and scale, and a failed spawn still retries on the next poll.
- **Effort:** S · **Risk:** low · **Upgrade class (guess):** compatible
- **Measure:** unmeasured. With 50 to 100 player stand-ins idle at a start town, measure the globalstep time of the poll over 5 minutes, before and after.
- **Confidence:** high

### P1-03 | Low | perf | Every wield entity runs a Lua `on_step` on every server step, only to notice an orphan

- **Verdict:** CONFIRMED — engine checked: `LuaEntitySAO::step` calls `luaentity_Step` for every registered entity (`reference_projects/luanti/src/server/luaentity_sao.cpp:223-225`), which looks up `on_step` and returns before any `lua_pcall` when it is nil (`src/script/cpp_api/s_entity.cpp:206-236`). So dropping `on_step` saves the protected call, the argument pushes and the Lua body per entity per step, but not the C++ entry and one `lua_getfield`. Also confirmed that a removed parent only detaches its children (`src/server/unit_sao.cpp:266-270`, `clearChildAttachments`), so some cleanup is required, as the comment at `apply.lua:39-43` says.
- **Where:** `mods/PLAYER/grug_visuals/apply.lua:38-74`
- **What:** Each armed NPC and each player carries one `grug_visuals:wield` entity. Its `on_step` adds dtime and returns until one second has passed, so each active wield entity costs one Lua `pcall` per server step. Hundreds of armed guards, bandits and vendors in loaded areas add up to hundreds of such calls per step that do nothing. The orphan case it guards is a parent removed without removing its child (a mob that dies or is removed).
- **Evidence:** `on_step` at `apply.lua:64-73`. `rg "_grug_wield_obj" mods` outside `grug_visuals` finds no removal at mob death or removal (finder; not rechecked).
- **Proposal:** remove the wield entity explicitly where the parent goes (the `grug_mobs` register wrapper's `on_die` / `on_deactivate`, and `grug_traders` vendors), then drop `on_step` or keep one shared, throttled sweep (a single 1 s globalstep over a weak set of wield entities that removes the unattached ones). Unloads need no handling, because `static_save = false` already drops the entity with its block.
- **Effort:** M · **Risk:** medium (a missed removal path leaves floating swords) · **Upgrade class (guess):** compatible
- **Measure:** unmeasured. Stand at a capital with about 200 active armed NPCs, and compare the server step time (`luaentity_Step` share) before and after.
- **Confidence:** medium

## Good to know

- Refresh design: the map window's sends are event-driven and budgeted at 8 checks and 2 builds per 0.1 s pass. world_map.md measures about 18 KB per send and up to about 1.1 MB per minute for one viewer in a walking party (Round 67). Accepted, not a finding.
- Minimap: every element remembers what was last sent, and only whole-pixel diffs go out. The cell texture is rebuilt about every 13 nodes. Clients never free these textures; world_map.md "Cells" documents and measures this.
- HUD bookkeeping: grug_quickbar and grug_displays own no HUD at all. The minimap, side elements, location banner and head-look override are created per join and their state is dropped on leave, so ids cannot leak across a relog.
- Character visuals: the texture list is written only when compose's key, the cloak, the wings or the Scout's back card change. `visual_size` is rewritten on every apply on purpose (mobs_redo resets it on dismount). The stored appearance JSON is written only when it differs.
- `grug_displays` keeps state only in node metadata. Projection entities are unsaved and rebuilt by an LBM that runs at every load. Puts, takes and moves check `grug_core.interaction_protected`.
- `grug_keys` reads `get_player_control_bits` for every player on every step, unthrottled on purpose (a key edge lasts one step).
- Engine source: `reference_projects/luanti` is now checked out; the verifier checked the `on_step` dispatch, child detachment on parent removal and the builtin `close_formspec`/death-screen paths (see P1-03 and the last backlog note). The finder's other engine remarks were not rechecked.
