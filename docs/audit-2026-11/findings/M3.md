## Findings

### M3-01 | Medium | determinism | The surface-skin opening reads the VoxelManip shell, so a border column's result depends on emerge order

- **Verdict:** CONFIRMED — the 3 x 3 neighbour test (`r6_settlement.lua:86-92`) reads `original_data` in the 16-node shell via `skin_context.native_class_at` (`:2468-2474`); the engine fills that shell from whatever is already in the map: `ServerMap::initBlockMake` (`src/servermap.cpp:229-254`) loads each shell block with `emergeBlock` or creates it with `createBlock`, and a new block is all `CONTENT_IGNORE` (`src/mapblock.cpp:110`); mapgen v7 writes base terrain only for the chunk's own x/z and one node above and below (`src/mapgen/mapgen_v7.cpp:536-539`). So an ungenerated neighbour reads ignore (run 0, never open) and a generated one reads its final content (air only where it opened or R5 kept native air), and the decision changes with emerge order. Order dependence is limited to the 3 x 3 path: the early return over the four planned neighbour heights (`:80-85`) is order-free.
- **Where:** `mods/MAPGEN/grug_mapgen/wp40/r6_settlement.lua:55-94` (`r9_native_air_run`, `r9_surface_skin_open`), `:2462-2499` (`skin_context`), `:2500-2533` (the per-column decision)
- **What:** Whether a land column's top is opened into a native cave (state 2) or sealed with a stone skin (state 1) is decided from `original_data` at positions outside the owner: the 3 x 3 neighbour columns (`x`/`z` in the 16-node shell for owner-edge columns) and depths 1-4 below a ground within four nodes of the owner's bottom. The shell holds a neighbour chunk's final content when that chunk was generated first and `CONTENT_IGNORE` when it was not (apart from the one v7 terrain row above and below the chunk), so the same seed gives a hole or a skin depending on which chunk the emerge thread made first.
- **Evidence:** `:2468-2474` `native_class_at` answers from `original_data[index_at(x, y, z)]` for any position inside the emerged bounds `eminx..emaxx`; `:86-92` rejects the opening when a neighbour's air run is under 4; `:2484-2491` treats `y < min_y` as "already the committed result of the preceding slice" (an order assumption); `:2511-2517` the pre-check reads `y >= eminy`. A generated neighbour in state 1 has filled its depths 1-3 with stone (`:2650-2674`), an ungenerated one reads ignore. Engine: `servermap.cpp:229-254`, `mapblock.cpp:110`, `mapgen_v7.cpp:536-539` (above). The module guide forbids exactly this: "Do not move cave connection decisions into the planner or infer them from emerge order" (`docs/technical/modules/mapgen.md:546-547`). Raised as MGT-09 (Low) in October, still present.
- **Proposal:** Decide the opening from order-free inputs only: the planned column tuple and native air read strictly inside the owner; treat a neighbour column or a depth outside the owner as "not open" (or as the planned value). Output changes for a few columns per world at chunk borders; everything else stays identical. Note: since an ungenerated neighbour already answers "not open", "treat outside as not open" equals today's result for the first-generated chunk of every pair, so the change is small.
- **Effort:** S · **Risk:** medium · **Upgrade class (guess):** compatible for new chunks (already generated chunks keep their result; a seam is possible only where a border column is regenerated) — the finder's "map reset" is stricter than needed; `r6_settlement.lua` is not in the preparation digest
- **Confidence:** high

### M3-02 | Medium | perf | The commit scan classifies both sides of every modified voxel, mostly for counters no production code reads

- **Verdict:** CONFIRMED — the two `classify` calls run for every modified owner voxel (`r6_settlement.lua:3539-3544`), also after both flags are set; `classify_runtime` (`r7_content.lua:436-446`) has no side effect other than a call counter and never fails for an engine CID (unknown CIDs return class 9), and the light fields come only from the CID row while the level matters only for liquids, which always have family > 0 (`r7_content.lua:377-379`), so the memo and the early skip leave every flag and VM call unchanged. Correction to the evidence: tools do call `session.metrics()` (`tools/r47_tc/forest.lua:44`, `tools/r37_mg/halo_evidence.lua:51`, `tools/r49_cache/portable_test.lua:93-96`, `tools/r47_td/density.lua:163`), but only for `templates`, `planner` and `p9g`; `rg dirty_columns|modified_voxels` finds no reader of the counters this loop fills.
- **Where:** `mods/MAPGEN/grug_mapgen/wp40/r6_settlement.lua:3516-3590`, `:1387-1390`; `mods/MAPGEN/grug_mapgen/wp40/r7_content.lua:434-443`
- **What:** For every owner voxel whose content or param2 changed, the last pass calls `classify` twice (nine results each, two `integer()` range checks and a counter per call in `classify_runtime`) to derive `light_changed` and `liquid_changed`, and keeps doing so after both are already true, only to fill the per-column `light_columns`/`liquid_columns` counters and `metrics_state`.
- **Evidence:** `:3539-3544` the two `classify` calls inside `for z / for x / for y` over the 80^3 owner; a surface chunk changes tens to hundreds of thousands of voxels (all R5 fill and clear). The counters go to `metrics_state` (`:3582-3590`), read only by `settlement.metrics` (`:3666-3675`), reached through `session.metrics` in `r6.lua:274-294`, which has no caller in `mods/`; the tools that call it read other keys (see verdict). Runs once per generated chunk in the emerge thread.
- **Proposal:** In runtime mode memoise the pair decision by `old_cid * 65536 + new_cid` (light and liquid depend only on the two content ids; the liquid level matters only for liquids, which set the flag anyway) and skip classification once `light_changed` and `liquid_changed` are both true. `content_changed`, `param2_changed`, `light_changed`, `liquid_changed` and therefore every VoxelManip call stay identical; only the unread column counters change.
- **Effort:** S · **Risk:** low · **Upgrade class (guess):** compatible
- **Measure:** unmeasured; `tools/mgprof` on one fixed seed, a 5 x 5 ring of surface chunks (one flat, one river, one forest area): time of the commit loop before and after, identical chunk digests.
- **Confidence:** high

### M3-03 | Medium | perf | The surface row of a column is selected two to three times per chunk by two separate selector objects

- **Verdict:** CONFIRMED — `r6_planner.lua:142` and `r6_settlement.lua:1188` each call `content.new_surface_selector`, which builds its own row tables and its own 65,536-slot steep memo (`r6_content.lua:771-1193`, `:909-959`), while `vegetation_rule` and `swamp_pools` are cached per seed (`:750-770`). The selector body reads only (x, z), the passed tuple values and seed-fixed state; the existing steep memo already assumes `terrain_y` is a function of (x, z). Caveat for the fix: `banded`, `snowed` and `iced` may return derived rows; a memo hands out the same table, which is safe only while no caller mutates a row (none was found in the callers cited).
- **Where:** `mods/MAPGEN/grug_mapgen/wp40/r6_content.lua:771-1193` (`new_surface_selector`, steep memo `:909-959`); callers `r6_planner.lua:142`, `:341`; `r6_settlement.lua:1188`, `:197`, `:1717`, `:2579`, `:2622`
- **What:** The planner and the writer each build their own selector (`new_surface_selector` returns a new closure with its own row tables and its own 65,536-slot steep memo), so every column's selection (three to four value-noise evaluations of four lattice hashes each, `coast_material_at`, `start_ground_at`, the steep class with eight column lookups, in a third of the columns four more lookups, the snow class) runs once in `column_tuple`, again in the strata pass, and again for each `analytic_p7_*` call; each vertically stacked chunk repeats all of it.
- **Evidence:** `r6_planner.lua:341` (6,400 columns per chunk), `r6_settlement.lua:197` (every admitted land column), `:1717` (`analytic_p7_material_ref`: once per decoration candidate at `:2887`, per sealed top at `:2579`, per snowy column at `:2622`, and per P9G and world-content query through `successor_context.analytic_p7_ref`). `vegetation_rule` and `swamp_pools` in the same file are already shared per seed (`r6_content.lua:750-770`); the selector is not. The selection is a pure function of (x, z) and the world: every caller passes the column's own tuple values.
- **Proposal:** Share one selector per seed (as `vegetation_rule` is) and give it a direct-mapped per-column memo of the selected row, keyed like the steep memo and guarded by the stored `id`, `water_y` and `terrain_y`. In `r6_settlement.lua:2622` test `rbase`/opcode 26 before the analytic call. Rows and output stay byte-identical; one steep memo instead of two.
- **Effort:** S · **Risk:** low · **Upgrade class (guess):** compatible
- **Measure:** unmeasured; mgprof, same seed and ring as M3-02, `plan_slice` plus strata time and the count of selector calls per chunk before and after.
- **Confidence:** high

### M3-07 | Medium | perf | Decoration placement builds every cell before the cheap rejections and asks the column exclusion once per voxel

- **Effort:** S · **Risk:** low · **Upgrade class (guess):** compatible
