# W1 — Mapgen wp13: town and capital building engine (verified)

- Finder model: claude-opus-5-5
- Verifier model: claude-opus-5-5
- Files read in full: 14 of 14; skimmed: none (the race tables of `palette.lua` and the long comment blocks of `parts.lua` read, not cross-checked against the node registry); not reached: none
- Summary: The engine is pure, deterministic and carefully commented. It builds the town and capital blueprints once per process: main builds every blueprint at load, and emerge rebuilds a lazy blueprint on first touch and again after the idle release. Only `city_edge.lua`, `city_green.lua` and `plot_approach.lua` run per mapchunk. Its main cost problem is the lack of any per-process sharing. Each capital's roster and full template set is parsed up to five times per process, against "reads the files once" in the format doc. Each `dressing.lua` instance regenerates its own tree pool. Template cells are resolved one by one with no memo, every buffer access builds a string key, and the tree fitter keeps scanning candidates it can no longer accept. All of these can be fixed with byte-identical output. Two of the per-chunk files (`city_edge.lua`, `plot_approach.lua`) are in the preparation-authority digest (`wp40/preparation_identity.lua:18`), so their small per-chunk savings belong in a map-reset round. A handful of dead helpers are left over from the removed generators: `parts.door`, `parts.bed` and `parts.double_door`, `dressing.stair_up` and `dressing.cobweb`, `layout.path`, `dwarf_dressing.stair_flight` and `decor_kit.rooms_from_corners`. `troll_palette.lua` ships in `mods/` but only tools read it. One design-doc number is stale: the corner skip is ±53, not ±45. Template errors stop the server at load, as the format doc specifies; no error path reaches generation, because main builds every blueprint before the first chunk.
- Verifier summary: 11 findings checked. W1-01 holds (5 parses per Lua environment, main plus the one pinned emerge thread), but one of its two proposals edits a digested file. W1-03's second cut, as the finder wrote it, would change which tree wins; it has been corrected. W1-05 holds, with one extra risk: a packed integer key would merge `-0` and `0`. The remaining findings are confirmed.

### W1-01 | Medium | perf | Each capital's roster and all its templates are parsed up to five times per process

- **Verdict:** CORRECTED — Count and load path confirmed. The proposal's upgrade class was wrong for one of its two options. Load path: `r7_runtime.lua:131` runs `world_assembly.lua` once per Lua environment. `world_assembly.lua:90` builds each capital's kit once, through `r7_capital_blueprint.kit`. The kit calls `library.composition(key)` (`r7_wp13_library.lua:47-50`, a plain `dofile`, no memo) and `dofile(<key>_districts.lua)` (`r7_capital_blueprint.lua:57,61`). The core (`highcourt.lua:65`) calls `templates.capital` inside its loader. Each of the four district files `dofile`s its own `highcourt_plot.lua`, whose loader calls `templates.capital` again (`highcourt_plot.lua:60`). `templates.lua` has no module-level cache (`M.capital` at `:805`). So there are 5 parses per environment for Highcourt, Dur Brannoc, Gor Drazhak and Nhal Veyr, and 2 for Lethariel and Kezamba (core plus one plot load). Later lazy rebuilds reuse the kit's closures (`r7_runtime.lua:265-267` passes `capital_kits[key]`) and do not re-parse. The engine gives every emerge thread its own `EmergeScripting` state that runs the mapgen scripts (`reference_projects/luanti/src/emerge.cpp:646-665`), and the game pins `num_emerge_threads = 1` (`minetest.conf:30`). The first option, letting `<capital>_districts.lua` load the plot module once and hand it to its four district modules, touches only non-digested wp13 files. There are two environments per server process: main and the single pinned emerge thread. The format doc says the opposite: "The game reads the files once at load" (`docs/technical/building-template-format.md:30`), and `docs/technical/modules/mapgen.md:465` says "`templates.town(id)` parses a town's layout and templates once".

### W1-02 | Medium | perf | Template cells are resolved one by one with no memo, and optional roles pay a linear role-list scan per cell

- **Verdict:** CONFIRMED — `M.part` (`templates.lua:688-722`) calls `resolve` per cell. `resolve` (`:624-668`) depends only on `(t, key, palette_of, race)`, and `palette_of` and `race` are fixed per `M.part` call. The palette handles are pure lookups: `node`, `maybe` and `variant` at `palette.lua:1031-1068` keep no state. So a per-call key memo gives identical names, param2 and first-error cell. A key is either always `late` or never (`entry.late`), so the late pass hits the same memo. `handle.maybe` and `M.new` use `contains` over `M.required`/`M.optional` (`palette.lua:954-959,1000-1021,1041`). `r7_settlement.lua:1620` calls `approach_palettes.new(profile.race)` per capital chunk. Neither `templates.lua` nor `palette.lua` is digested.
- **Where:** `mods/MAPGEN/grug_mapgen/wp13/templates.lua:688-722` (`M.part`, calling `resolve` per cell) and `:624-668` (`resolve`); `wp13/palette.lua:954-959`, `:1034-1043` (`handle.maybe`) and `:1017-1021` (`M.new`)
- **What:** `M.part` calls `resolve(t, key, palette_of, race)` for every grid cell. The result depends only on the legend key, because race and palettes are fixed per placement. Yet each call repeats:
  - the legend lookup;
  - the `palette_of(channel)` closure call;
  - the palette call;
  - `parts.param2_kind` and `orientation(entry.o)`, which runs a `string.match`.

  For an optional role, `palette.maybe` additionally runs `contains(M.required, role)` and then `contains(M.optional, role)`, linear scans over 77 + 37 names, once per cell. `palettes.new` runs the same scans for every role it binds (`:1017-1021`, about 114 x 114 / 2 comparisons per handle). `wp40/r7_settlement.lua:1620` calls it once per capital chunk (`approach_palettes.new(profile.race)`), and the loaders call it once per named palette.
- **Evidence:**
  - `parts.lua:327-329` records that the buffer writes run "hundreds of thousands per construction, twice per process".
  - Main builds every blueprint at load (`wp40/r7_runtime.lua:209-215`). Emerge rebuilds a lazy one on its first chunk and again after `IDLE_RELEASE = 64` idle plans (`wp40/r7_settlement.lua:130-134`, `:1436-1442`).

- **Proposal:**

- **Effort:** S · **Risk:** low · **Upgrade class (guess):** compatible. Neither file is digested; the layout cache rebuilds once.
- **Measure:** unmeasured. Use `os.clock` around one capital core build (`kit.core`) and one plot build on any seed; count `resolve` calls before and after with a counter.
- **Confidence:** high

### W1-03 | Medium | perf | The town tree fitter scans up to 164 candidates in full, including those it can no longer accept

- **Verdict:** CORRECTED — The first cut is safe; the second, as written, changes the chosen tree. Selection in `dressing.lua:466-474` is in two steps. First, a candidate with `skipped * 4 <= leaf_count` is taken at once (`break`). Otherwise the candidate with strictly fewest `skipped` among those with `skipped * 2 <= leaf_count` wins, and the earlier one wins ties. Cut 1 (return `nil` once `skipped * 2 > leaves`) only drops candidates that can never be picked, so it is safe, also in `city_green.fit` (`city_green.lua:326`). Cut 2 ("stop once a `best` exists and `skipped >= best_skipped`") is **not** safe. `leaf_count` differs between pool entries, and a later candidate from a leafier entry can have `skipped >= best_skipped` and still pass `skipped * 4 <= leaf_count`. That candidate wins today through the `break`. Example: `best` has 10 leaves and 3 skipped; a later entry has 100 leaves and 3 skipped. Today the second wins; with cut 2 the first wins. Corrected rule: stop a candidate when `skipped * 2 > leaves`, or when `best` exists, `skipped >= best_skipped` and `skipped * 4 > leaves`. `skipped` only grows, so such a candidate can neither replace `best` nor trigger the early accept.
- **Where:** `mods/MAPGEN/grug_mapgen/wp13/dressing.lua:401-474` (`M.grown`: `try` and the candidate loop); the same shape in `wp13/city_green.lua:298-348` (`fit`)
- **What:** `M.grown` builds 4 + 5 x 8 x 4 = 164 candidates (`:452-463`) and runs `try` on each in turn. `try` walks every cell of the pool entry and, for each one, calls `buf:at` twice. Each `buf:at` builds a string key. A candidate is accepted only when `skipped * 2 <= leaf_count` (`:469-470`), but `try` counts leaves to the end and only then lets the caller compare. A candidate whose skipped leaves already exceed half the entry's leaves still scans all its remaining cells and its root runs, and builds a `writes` table. The leaf total is a property of the pool entry, the same for every turn and position. `city_green.fit` has the same late check (`:326`); it runs per chunk through the overlay, behind its viability memo.
- **Evidence:**
  - `dressing.lua:452-463` builds the candidate list.
  - `:403-424` is the per-cell loop with `buf:at(bx, 0, bz)` and `buf:at(bx, by, bz)` (string keys, `parts.lua:694-696`).
  - `:469-470` holds the acceptance rule.
  - Callers: every `layout.green` slot (`layout.lua:201-215`), the orchards, groves and woods (`layout.lua:286-437`), and every planted template stem (`templates.lua:712-714`). They all run in every blueprint build.
- **Proposal:**
  - Store each pool entry's leaf total when the pool is built (`pool_of`, `:330-348`, and `city_green.lua:165-183`).
  - In `try`/`fit`, return `nil` as soon as `skipped * 2 > leaves`.
  - In `M.grown` only, pass `best_skipped` into `try` and stop a candidate once `best` exists, `skipped >= best_skipped` **and** `skipped * 4 > leaves`. Without the last condition the cut drops candidates that the early-accept `break` would pick.

  With these conditions the cuts reject only candidates the current rule never picks, so the chosen tree and its writes stay identical.
- **Effort:** S · **Risk:** low (proof: the selection rule at `:466-472` is unchanged; the second cut must carry the early-accept condition) · **Upgrade class (guess):** compatible (neither file is digested)
- **Measure:** unmeasured. Count `try` cell iterations and time `layout.green` in one capital core build (Highcourt) before and after.
- **Confidence:** high (that the corrected cuts change nothing); medium (that the saving is large)

### W1-05 | Medium | perf | Every buffer write and read builds a string key; numeric keys would remove most allocations of a construction

- **Verdict:** CONFIRMED — `parts.lua:675,695` build `x .. ":" .. y .. ":" .. z`. The other key users are exactly those listed, plus `parts.lua:762-773` (`Buffer:cells` reading `w.key`, `grown_wood`, `grown_leaves`) and `tools/r47_tc/portable_test.lua:641-684`. Output order comes from `self.order` (`:687-691`). One extra risk the finder missed: Lua 5.1 and LuaJIT format `-0` as `"-0"`, so today a cell at `x = -0` and one at `x = 0` are two keys. The packed integer key would merge them. `dressing.lua`'s `turn` (`:359-362`) produces `-x`, and `r7_settlement.lua` already notes that "a signed zero would be another key". So "byte-identical" holds only if no `-0` coordinate reaches `put`/`at` today. Before the switch, add a temporary check that compares the cell list on every blueprint.
- **Where:** `mods/MAPGEN/grug_mapgen/wp13/parts.lua:641-696` (`Buffer:put`, `Buffer:at`); the same string keys in `dressing.lua:419,498-505` (`grown_leaves`, `grown_wood`, `tree.writes[].key`) and `layout.lua:154` (`tree_room`)
- **What:** `Buffer:put` and `Buffer:at` both build `x .. ":" .. y .. ":" .. z`, one string allocation and hash per call, and each new cell is a 5-field table. These are the innermost calls of every blueprint build:
  - every template cell (`templates.lua:702`);
  - every stamp (`parts.lua:851`), including the re-key of each cell on stamping;
  - every tree probe (W1-03);
  - every free-cell test in the dressing.

  `parts.sort_cells_zyx` (`:804-834`) already packs a position into one exact integer, `((z + 32768) * 65536 + (y + 32768)) * 65536 + (x + 32768)`.
- **Evidence:** `parts.lua:675` and `:695` build the keys. The callers listed above all run in every build, and the build counts are as in W1-02. `rg -n "\.cell\[|grown_leaves\[|grown_wood\["` over `mods/` finds the string-key users only in `parts.lua`, `dressing.lua:419,504,505` and `layout.lua:154`. Tools that read `buf.cell` directly: `tools/r47_tc/portable_test.lua` and `tools/building_templates/freeze_build.lua`.
- **Proposal:** Key `cell`, `grown_wood` and `grown_leaves` by the packed integer that `sort_cells_zyx` uses. Coordinates stay far inside ±32768: a pad is at most a few hundred nodes and y is part-local. Change the four key builders together and update the two tools. Output order comes from `self.order`, so the cell lists stay byte-identical, provided no signed zero reaches the buffer (see the verdict).
- **Effort:** M · **Risk:** medium (every key user must move at once; non-integer coordinates must not occur, so an assert in `put` is advisable; `-0` and `0` would merge) · **Upgrade class (guess):** compatible
- **Measure:** unmeasured. Use `os.clock` and `collectgarbage("count")` around one full capital kit build in main, before and after.
- **Confidence:** medium

## Good to know

- **Where the cost is.** Town and capital construction is once per blueprint per process: main builds all at load (`wp40/r7_runtime.lua:209-215`), and emerge rebuilds lazily on first touch and after 64 idle plans (`wp40/r7_settlement.lua:130-134`). Only `city_edge.cells`, `city_green.cells`/`cover` and `plot_approach.surface` run per mapchunk, and `r7_settlement` gates them by a per-footprint write span (`:1599-1601`).
- **Environments (verifier).** A "process" here means one Lua environment. The server runs main plus one emerge state per emerge thread (`reference_projects/luanti/src/emerge.cpp:646-665`), and the game pins `num_emerge_threads = 1` (`minetest.conf:30`), so every per-environment load cost is paid twice per server start.
- **Broken templates.** They stop the load (format doc §1). Main prepares every blueprint before the first chunk, including on a layout-cache hit, so no template or palette error can first appear in an emerge thread.
- **Preparation authority.** In wp13, only `city_edge.lua` and `plot_approach.lua` are in the strict authority digest (`wp40/preparation_identity.lua:18`). In wp40, `r7_capital_blueprint.lua`, `r7_capitals.lua`, `world_assembly.lua` and `r7_runtime.lua` are in it too (`:14-17`), so a sharing fix must not be threaded through them. Every other `.lua`, `.tpl`, `.layout` and `.roster` below the mapgen mod is in the layout-cache key (`wp40/layout_cache.lua:45-63`): a change there costs one layout rebuild at the next start, not a refusal to start. The preparation identity also digests the layout texts (`r7_runtime.lua:334-342`), which stay the same when output is identical.
- **Determinism.** No `x ^ 2`, `math.random` or time source in the package. Every `pairs` either builds a map, feeds a sort (`use_key`, `all_used`, `city_edge.names`) or iterates disjoint prefixes (`parts.lua:337`). Float use (`patch_weight`, `walk_at`, `nearest`, `inside_city`) is plain IEEE arithmetic and `sqrt`, identical in LuaJIT and PUC.
- **`parts.lua` and `palette.lua` belong to every settlement.** POIs, camps (`r58`/`r63`), the PvP blueprint and `r7_settlement` load them too. Any table change there touches far more than the towns.
