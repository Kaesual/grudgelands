# P2 — Jobs, Miner's Guild, achievements (verified)

- Finder model: claude-opus-5-5
- Verifier model: claude-opus-5-5
- Files read in full: 34 of 38; skimmed: `mods/PLAYER/grug_jobs/basic_recipes.lua` (data rows), `mods/PLAYER/grug_guild/machines_data.lua` (generated node boxes), `mods/PLAYER/grug_achievements/catalog.lua` (data rows; header and counters read), `mods/PLAYER/grug_jobs/station_visuals.lua` (node boxes); not reached: none
- Summary: The three mods are in good shape: no globalstep does per-player work beyond the Basic-unlock slot pass and the open-furnace pass, job and guild state is versioned or self-healing (unreadable jobs and queue entries are dropped with a warning, unknown recipe ids refund, unknown cloaks and achievement ids are ignored), and reward flows check room before they spend. The most useful items are server-side: an achievement counter rebuilds the whole Character page on every eligible kill (twice for a family kill) whenever that page was the last one viewed, even with the window closed; the Basic-unlock scan copies every inventory list and a ~4.7 KB meta string after every dug node; and the personal workspaces of the authored public furnaces keep one record per player forever in node meta, which the map-reset pack pass does not read, so their items go with the map (the upgrade contract covers this only through its general "nodes outside the claims" exclusion). There is also a dead "public hearth" seam in the vendored furnace plus a redundant LBM, and a no-op `refresh_position`. The design docs (miners_guild.md, professions.md, items-professions.md) match the code closely; ui-looks.md has one stale count.

## Findings

### P2-01 | Medium | perf | Every eligible kill can rebuild the whole Character page (up to twice), window open or not

- **Verdict:** CORRECTED — the call chain holds (`grug_achievements/init.lua:141-163, 303-312`, `grug_inventory/pages.lua:516-521`; sfinv keeps `context.page` until `set_page` or leave, `mods/BASE/sfinv/api.lua:99,159,178-179`; `kill:animal`/`kill:zombie` and the five `kill:family:*` counters are all catalogue counters). Engine checked: `ObjectRef:set_inventory_formspec` sends only when the string differs from the stored one (`reference_projects/luanti/src/script/lua_api/l_object.cpp:1750-1755`), so the full build always runs but a packet goes out only when a row on the shown achievements page (7 per page, `init.lua:456`) changes its status text. The proposal's "skip when the formspec is not open; the page builds fresh on the next open anyway" is wrong: the client opens the inventory from its stored formspec without asking the server (`src/client/game_formspec.cpp:312-350`), so a skipped refresh would show stale progress. Only the coalescing part of the proposal stands.
- **Where:** `mods/PLAYER/grug_achievements/init.lua:141-163`, `:274-312`; `mods/PLAYER/grug_inventory/pages.lua:516-521`
- **What:** `grug_achievements.add` calls `counter_changed`, which calls `grug_inventory.refresh_character_tab(player, "achievements")` whenever no tier was earned. That rebuilds the full sfinv inventory formspec when the player's sfinv context still says Character page / Achievements mode, and sends it when it differs from the last one. sfinv keeps `context.page` after the window closes (it changes only in `set_page`, `mods/BASE/sfinv/api.lua:99,159`). So a player who last looked at Achievements gets a full page build on every eligible kill, and a send whenever a visible progress line moved. A kill of a family mob (boar, rat, skeleton, golem, construct) feeds two counters (`kill:animal` or `kill:zombie` plus `kill:family:<f>`), which means two builds (and up to two sends) per kill. A rare kill can add a third.
- **Evidence:** `kill_counters` (init.lua:282-297) always adds `kill:<class>` and adds the family/group counter when wanted. The eligible-kill hook (init.lua:303-312) calls `add` once per counter. `add` → `counter_changed` → `refresh_character_tab` (init.lua:152-154). The hook runs for every credited participant of every mob death (`grug_mobs.award_kill_xp`, `mods/ENTITIES/grug_mobs/init.lua:240-260`), so every party member pays this, 100 players fighting.
- **Proposal:** Coalesce the refresh: have `counter_changed` set a per-player "achievements dirty" flag and let the end of the kill hook (or one `core.after(0)` per player) call `refresh_character_tab` once. Do not skip the refresh for a closed window: the server cannot see the inventory open, and the client shows the stored formspec. The counters, tiers, feed lines and the page content must stay identical.
- **Effort:** S · **Risk:** low · **Upgrade class (guess):** compatible
- **Measure:** unmeasured. On a larger machine, 20 stand-in players with the sfinv context on Character/Achievements each kill 100 boars. Count `sfinv.get_formspec` builds and `set_player_inventory_formspec` calls before and after (expected about 2,000 → 1,000 builds).
- **Confidence:** high

### P2-03 | Medium | persist | Public furnace node meta grows by one never-deleted record per player who ever used it

- **Verdict:** CONFIRMED — `save` (`workspaces.lua:72-91`) only writes; the only `set_string` of a record key is line 90; the only other reader, `station_contents` (`:330-345`), runs on dig/blast, which public stations do not see. `save` also writes a `process`-only record for player-placed (non-personal) furnaces, so those grow per viewer too until dug.
- **Where:** `mods/PLAYER/grug_jobs/workspaces.lua:72-91`, `:216-221`, `:330-345`
- **What:** `save(ctx)` writes `core.serialize({lists = …, process = …})` under `grug_jobs:workspace:<player>` on the station's node meta at every change, close and leave. Nothing ever clears the key, even when every list is empty and the fuel is out. A capital furnace that hundreds of players touch over months accumulates hundreds of records, each a few hundred bytes even when empty (6 or 7 slot strings plus `process` with `last`, `fuel`, `fuel_total`, `progress`, `recipe`). All of it rides in that mapblock's metadata on every save and load of the block.
- **Evidence:** `save` only compares with the stored string (line 90) and never deletes. `detach` saves (line 218) and `on_leaveplayer` → `detach` (lines 298-300). There is no `set_string(key, "")` in the file (`rg -n 'set_string\(key' mods/PLAYER/grug_jobs/workspaces.lua` gives only line 90).
- **Proposal:** In `save`, when every list is empty and `process.fuel` is 0 (nothing in progress), write `""` (delete the key) instead of the record. `open` already treats a missing record as `{}` (line 269), so behaviour is identical for the player. A one-time LBM pass could prune empty records already stored.
- **Effort:** S · **Risk:** low · **Upgrade class (guess):** compatible
- **Confidence:** high

### P2-04 | Medium | perf | The Basic-unlock scan after every dug node copies every inventory list and a ~4.7 KB meta string

- **Verdict:** CONFIRMED — `register_on_dignode` marks the digger dirty (`basic_unlock.lua:395-397`), the slot pass scans dirty players (`:399-414`), and `scan_held` reads `HELD_KEY` (`:194`) and walks `inv:get_lists()` (`:197`). Engine checked: `InvRef:get_lists` builds a new table with one `LuaItemStack` userdata per slot of every list (`src/script/lua_api/l_inventory.cpp:234-244`, `src/script/common/c_content.cpp:1623-1630, 2096-2103`). The 4.7 KB figure is the module guide's (`items-professions.md:234`).
- **Where:** `mods/PLAYER/grug_jobs/basic_unlock.lua:191-211`, `:366-414`
- **What:** `register_on_dignode` marks the digger dirty (line 395-397), so a mining player is scanned once per 0.5 s slot. On top of that, every player is swept every 10 s. Each scan calls `inv:get_lists()`, which copies every list (main, the bags, equipment, hotbar store, overflow, target…) into fresh ItemStack userdata. It also reads `player:get_meta():get_string(HELD_KEY)` only to test `== ""`. That string is about 4.7 KB once every ingredient has been held (`docs/technical/modules/items-professions.md` "The Basic unlock"). The held set is already cached in `cached[name]`, so the read buys nothing after the first scan. For a long-time player the scan almost never finds a new token.
- **Evidence:** basic_unlock.lua:194 (`local first = player:get_meta():get_string(HELD_KEY) == ""`) and :197-209 (`for _, list in pairs(inv:get_lists())`). The slot pass (lines 399-414) visits one fifth of the players every 0.1 s.
- **Proposal:** (1) Keep `first` in memory: set it at the session's first `load`, and clear it after the first `save`. (2) In the dig hook, mark dirty only when the dug node's drop names (`core.registered_nodes[oldnode.name].drop`, or the name) yield a token from `tokens_of` that `held` lacks. Inventory actions and deliveries still mark dirty, and the 10 s sweep still catches loot from other paths. What must stay identical: the unlock set and the feed lines. Item arrivals outside the dug node's drop table (for example Remains loot) would be noticed by the sweep up to 10 s later instead of 0.5 s.
- **Effort:** S · **Risk:** low · **Upgrade class (guess):** compatible
- **Measure:** unmeasured. 50 stand-in players each dig one stone node per 0.5 s for 60 s, with full bags and a full held set. Compare the Lua time in `scan_held` (or the count of `get_lists` calls) before and after.
- **Confidence:** medium

### P2-02 | Low | persist | Items in the personal workspaces of authored public furnaces are lost at a map reset; the contract covers it only implicitly

- **Verdict:** CORRECTED — `tools/migration/pack.py` read in full (329 lines): the only map reads are `scan_claim` over `area_blocks(claim)`/`in_area(claim, …)` (`:143-216`); workspace records are packed only inside claim areas (`:204-213`), so records at the public sockets are not packed. But the loss is not undeclared: upgrade-contract.md:277 lists "nodes outside the claims" under **Not packed**, which covers every node meta outside claims, these records included; the "durable" wording in inventory_equipment.md:827-834 is about normal play. What is missing is that the contract and the design never name the public workspaces, whose items players never placed as nodes and cannot pick up by digging. That makes it a documentation/design decision on a rare event (a map reset), so Low, not Medium. Side note: the pass gives a workspace record found inside a claim to the claim owner (`build`, `:247-251`), not to the record's player.
- **Where:** `mods/PLAYER/grug_jobs/workspaces.lua:72-91` (records in node meta `grug_jobs:workspace:<name>`), `:258-282`; `tools/migration/pack.py:143-216, 236-251`; `docs/technical/upgrade-contract.md:218-227, 277-279`
- **What:** The capital/POI furnaces and dual furnaces are personal workspaces. Each player's inputs, fuel and finished output live in that station's node meta. The map-reset pre-pass packs node inventories and workspace records only inside housing-claim areas (x/z ± 50 around each claim). Authored public stations stand in towns, outside claims, so a player's smelted bars or food left in a capital furnace go with the map. The upgrade contract's §3.5 excludes "nodes outside the claims" in general but does not name this case, and inventory_equipment.md promises "durable inputs, outputs … per player".
- **Evidence:** `pack.py` `area_blocks(claim)` / `in_area(claim, …)` (lines 143-153) are the only map reads, and `scan_claim` iterates claim areas only. `workspaces.lua:263`: `personal = grug_jobs.is_public_station(station, pos)`. The public positions are the settlement sockets (`station_nodes.lua:192-204`), which are not claims.
- **Proposal:** Decide with the design owner: either (a) extend the pre-pass to read the blocks of every public-station socket position and pack each `grug_jobs:workspace:<name>` record that holds items as a `recovered:<name>:…` row for that player (and give in-claim records to their player, not the claim owner), or (b) name the public workspaces in upgrade-contract.md §3.5 "Not packed" and in inventory_equipment.md, and warn players before a reset. The rest of the pass must stay byte-identical.
- **Effort:** M (a) / S (b) · **Risk:** medium · **Upgrade class (guess):** map reset
- **Confidence:** high

## Backlog notes

It is unreachable because the same call checked `queue_full` first and nothing can fill the queue in between (`mods/PLAYER/grug_jobs/jobs.lua:973,1008,1018-1020`). Still, an explicit give-back like `operation_jobs.lua:181-184` would make it safe.

- Code comment drift: the catalogue says Ore Sense marks "the nearest target deposit" (`mods/PLAYER/grug_guild/catalog.lua:106-107`), but the code and spec §7 pick a random deposit (`effect.lua:329-373`).

- Kill-counter writes: a family kill writes two player-meta ints per credited participant (`grug_achievements/init.lua:161`). This is fine in itself and only matters together with P2-01.

## Good to know

- Saved state is robust. An unreadable job or queue entry is dropped with a warning (`jobs.lua:114-125,155-171`). A job whose recipe id no longer exists (recipe ids are derived from output plus sorted ingredients, `registry.lua:179-186`) refunds what it has not delivered. Unknown cloak ids are ignored and an unknown selected cloak reads as "none" (`grug_achievements/core.lua:207-217,347-353`). A tier key of a removed achievement is simply never read, and an unknown queued manual id is dropped at join (`init.lua:238-246`). The guild's player-meta keys hold no position, so nothing guild-side is map-bound except the Remains nodes, which turn back into rock through their node timer after a restart (`effect.lua:287-299`).
- Reward flows check room before they take or spend: `start_job` (`output_fits`), `cancel_job`/`cancel_queued` (dry-run `fits`), `start_operation`, `buy`, `stonewright_make`, and `trade_in` (server-side recount). Double clicks are blocked by build serials (`ui.lua:582-594`, stop field named by the job's start, queue cancel by entry id).
- There is no guild hook on dig, place or craft. Reputation changes only through the trade-in, `/guild_rep` and spending. Achievements have no globalstep; they run per event plus one settle pass at join.
- Engine behaviour: the finder could not check it; the verifier checked `get_lists` copying (P2-04), the inventory-formspec resend rule and the client-side inventory open (P2-01) in `reference_projects/luanti`.
- miners_guild.md §§4-10, professions.md §1.2-1.5 and items-professions.md ("Crafting jobs", "The Basic unlock", "Miner's Guild") match the code, numbers included (ranks, exchange rates, consumable parameters, Remains loot, Stonewright table, queue of 5, thresholds 10/15/20/25/30, durations, the 4-node station check, the 0.5 s/10 s scan cadence).
