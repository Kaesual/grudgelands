### P5-01 | Medium | security | Mail text limits count malformed UTF-8 runs as one character (4,000-char limit bypass, invalid UTF-8 stored)

- **Verdict:** CORRECTED — the claim holds; only the `grug_mail/model.lua` line numbers were wrong (the code is at `:59-104` and `:111-118`, not `:234-294`). Worked by hand: the bytes `41 80 80 80` ("A" and three continuation bytes) against `CHAR = "[%z\1-\127\194-\244][\128-\191]*"` (`model.lua:59`): `41` matches the lead class `[\1-\127]`, the greedy `[\128-\191]*` then takes all three `80`, so `gmatch` yields one 4-byte match; `text_length` (`:61-65`) counts 1; `clean` (`:84-104`) keeps it, because its only drop test is `#char == 1` and a control byte; `truncate(text, max)` (`:70-80`) reads `4 * max` bytes and counts it as 1. Stretched to "A" plus 39,999 `80`: the window's `take` (`window.lua:697-703`) keeps `M.truncate(field, M.DRAFT_MAX)`, `DRAFT_MAX = 10000` (`model.lua:36`), so the first 40,000 bytes, all one "character"; `send_letter` (`api.lua:135-138`) runs `check_body` (`model.lua:111-118`), which measures 1 <= 4,000 and stores all 40,000 bytes. A subject goes the same way: 240 bytes (`4 * SUBJECT_MAX`) as one character. For comparison, the same 4 bytes in `grug_accounts` `M.clean` (`grug_accounts/model.lua:52-81`): `size(0x41) = 1` differs from `#char = 4`, so the match is dropped; valid `E2 82 AC` (the euro sign) has `size(0xE2) = 3 = #char` and is kept. The engine does not stop such bytes: `reference_projects/luanti/src/network/serverpackethandler.cpp:1250-1272` reads each field with `sanitize_untrusted` (`src/util/string.cpp:1005-1038`, which removes only control bytes below 32 apart from tab, line feeds and the escape) and limits only the whole submit to 640 KiB; no UTF-8 check. Severity stays Medium: a limit bypass that only a modified client reaches, costing storage, log size and bridge traffic (each mailbox still holds at most 50 player letters), with no item or money effect.
- **Where:** `mods/PLAYER/grug_mail/model.lua:59-104` (`CHAR`, `text_length`, `truncate`, `clean`), used by `check_body` (`model.lua:111-118`), `send_letter`/`send_ticket`/`report_letter` (`api.lua:135-138, 394-398, 428`), the window drafts (`window.lua:697-706`) and the bridge's `C.plain`/`line`/`subject_of`/`body_of` (`grug_bridge/commands.lua:21-62`)
- **What:** `CHAR = "[%z\1-\127\194-\244][\128-\191]*"` matches any lead byte (ASCII included) followed by any number of continuation bytes, and `clean` keeps such a match whole. "A" followed by 39,999 bytes `\128` therefore counts as one character. The window keeps a draft up to `truncate(text, DRAFT_MAX)` = the first 40,000 bytes, so a modified client can store a 40,000-byte body that `check_body` measures as 1 character. The same applies to subjects: 240 bytes against the 60-character rule. Stored letters and tickets then hold invalid UTF-8. `grug_bridge/link.lua:27-67` (`L.valid_utf8`) exists only to repair this before the JSON reaches the website, and it expands each stray byte to 3 bytes. The legitimate worst case is 4 bytes a character (16 KB a body); with this gap, mailboxes (50 player letters), tickets, server log lines (`log_ticket` logs the whole body) and bridge events grow about 2.5× beyond that.
- **Evidence:** `model.lua:59` (pattern), `model.lua:84-97` (`clean` keeps `char` whole unless it is one control byte), `model.lua:70-80` (`truncate` reads `4 * max` bytes), `window.lua:703` (`take(session.draft, "body", "mail_body", M.DRAFT_MAX)`). The correct variant already exists: `grug_accounts/model.lua:52-81` keeps a character only when `#char == size(byte)`. Its comment ("as grug_bridge's C.plain cleans it", `model.lua:57`) claims both cleaners do the same thing, but they have drifted apart. `docs/technical/modules/platform.md:319` ("M.clean keeps a stray lead byte") notes the symptom, not the size bypass.
- **Proposal:** Make `M.clean` (and the `CHAR` walk in `text_length`/`truncate`) drop a match whose byte count does not fit its lead byte, as `grug_accounts` `M.clean` does. Then point `C.plain` and the accounts model at one shared helper (for example in `grug_core`) so the two cannot drift again; that helper must take only the byte-length rule, because the two cleaners differ on purpose elsewhere (mail keeps line ends where `multiline`, and the accounts cleaner removes colour escapes whole, see the backlog note on `subject_of`). Valid UTF-8 input must give byte-identical output; keep `L.valid_utf8` as a safety net for old stored texts.
- **Effort:** S · **Risk:** low · **Upgrade class (guess):** compatible
- **Confidence:** high

### P5-02 | Medium | perf | One mailbox click deserializes the whole mailbox five times (and the broadcasts twice)

- **Verdict:** CONFIRMED — `S.box` (`store.lua:48-53`) calls `load` (`:25-35`, `core.deserialize` without a cache) each time. A Letters-row click runs `selected_letter` (`window.lua:718-720`), `grug_mail.open_letter` (`api.lua:217-226`), which for an unread letter also runs `refresh_count` -> `unread_count` (`api.lua:33-38`, with `S.broadcasts()`), then the redraw's `counts_of` (`window.lua:640-647`, `S.broadcasts()` again) and `letters_tab` (`:291-292`): five box reads for an unread letter, four for a read one. Admin Mail: `filtered` and the open-count loop each call `grug_mail.tickets()` and the selected entry `grug_mail.ticket` (`api.lua:444-446`) a third. The cost is per click, not per tick, so it matters only for large mailboxes (the 50-letter cap of player letters, and more with P5-01); Medium as "a clear improvement" fits.
- **Where:** `mods/PLAYER/grug_mail/window.lua:718-720, 747-781, 640-654, 291-293`; `api.lua:33-38, 217-226`; `store.lua:71-76, 120-124`; admin tab `admin.lua:262-311`
- **What:** `S.box(name)` reads the mod-storage string, runs `core.deserialize` on the whole mailbox and prunes it on every call. A letter-row click in the Letters tab calls it five times: `selected_letter` (1), `open_letter` (2), its `refresh_count` → `unread_count` (3), `counts_of` while drawing (4) and `letters_tab` (5). It also saves once and deserializes `broadcasts` twice. `send_letter` reads the recipient's box twice. A mailbox can hold 50 player letters of up to 16 KB each (legitimately; 40 KB each with P5-01) plus unlimited admin/NPC letters for 30 days, so each read parses up to about 0.8 MB of Lua source. The Admin Mail tab deserializes the shared `tickets` list (no limit, 30 days) three times per draw: `filtered`, the open count loop and `grug_mail.ticket`.
- **Evidence:** the call chain above. `store.lua:48-58` is `load()`, which calls `core.deserialize` on every call, with no cache. Callers: every mailbox formspec event (`window.lua:908-943`) and every Admin Mail event.
- **Proposal:** Read the box once per event and pass it down: `letters_event` → `open_letter(player, id, box)`, and `window_formspec` computes the counts from the same box. Alternatively, add a per-name cache in `store.lua` that `save_box` and `core.after(0)` clear. Do the same for `broadcasts` and `tickets`. Prune semantics (prune at read, save when pruned) and every stored byte must stay identical.
- **Effort:** S · **Risk:** low · **Upgrade class (guess):** compatible
- **Measure:** unmeasured. On a larger machine, fill one mailbox with 50 letters of 4,000 characters each (a fixture writing `box:<name>` directly), then time `core.on_player_receive_fields` for a Letters-row click before and after with `core.get_us_time()` around the handler. Probe: `tools/r48_mail` stub engine.
- **Confidence:** high

## Good to know

- Mail item safety is sound. Send captures the slots as strings and replaces them through `take_with_inventory` with expected stacks (atomic, no callbacks). Take all saves the emptied letter before giving and puts back anything that did not fit. Draw serials catch a double Send in the window and in Admin Mail. Attachments left in `grug_mail_out` by a disconnect or death go back at the next join or at death.
- Offline and unknown recipients: player mail needs the recipient in the `factions` index (filled at join and faction choice). Unknown and other-faction names get the same refusal. Admin and system mail falls back to `core.player_exists`. Mailboxes of players who never return are never pruned. This is intended (mail.md §10: no pass over every player), but such keys stay in mod storage for good. Each is bounded: 50 player letters plus 30 days of system letters.
- Parties and clans are not looked up in combat, XP or loot (`rg grug_parties mods` hits only the map, Expeditions and the clans). Membership checks are O(1) table reads; the cost sits in `view()` (P5-03).
- The bridge contract checks out on: event queue, ack, resend bounds, `dropped_events`, 401/409 handling, back-off, `next_ms` clamp, result forgetting, the at-most-once ledger, ban list storage and disconnect, the `accounts` ordering (ban list → accounts → resync → commands), the reward-catalogue resend, online-row fields and their resend on a binding change, all `account.link_answer` state rules, `account.set_password` checks, and the logs (no code, password or entry is ever logged).
- The engine submodule `reference_projects/luanti` was empty when the finder ran. The verifier checked the formspec field path (P5-01: only a 640 KiB total limit and control-byte removal, no UTF-8 check) and `core.write_json`'s output (backlog note above) in it.
