# C2 — grug_abilities (verified)

- Finder model: claude-opus-5-5
- Verifier model: claude-opus-5-5
- Files read in full: 12 of 14; skimmed: `charge_path.lua` (lines 1-200 and 495-541 read, the hop/hole planner body 200-495 skimmed: pure Lua over a cached `world`, no engine calls), `cooldown_math.lua` (constants header 1-39 skimmed; all functions read); not reached: none
- Summary: The package is in good functional shape: every class kit number I checked (cost, cooldown, occupied time, coefficient, radius, talent ranks) matches classes.md §3-§5, scout.md §2 and ability_targeting.md. Delayed effects re-fetch their players by name, and the two hpchange callbacks are plain loggers that respect the modifier contract. The most valuable items are: (1) a reconnect resets every cooldown, charge and the mana pool (Sprint's 300 s, every 60 s ultimate; this is the open question CMB-10, with concrete stakes); (2) per-step input/HUD work that repeats the same wield, unlock and privilege reads two or three times per player per server step, and a 0.5 s pass that handles every player in one step and recomputes max mana up to three times per player; (3) the 8 s enemy/ally "target memory" is write-only in the shipped game, although the docs say it feeds the Target Frame (and the module guide says friendly casts fall back to it); (4) a set of dead talent keys and definition fields that no talent produces any more. init.lua has a clean natural split along its section headers. Engine claims could not be checked by the finder; the verifier checked the privilege path in `reference_projects/luanti` (see C2-02).

## Findings

### C2-01 | Medium | security | A reconnect resets every cooldown, every swing charge and the mana pool

- **Verdict:** CONFIRMED — `init.lua:3087-3105` drops `mana`, `cooldowns`, `charges`, `cast_intervals`, `cast_clock`; join calls `refill_mana` (`:3053`); cooldowns live only in the Lua table `cooldowns` (`:1433-1434`), no meta copy exists anywhere in the package; death (`:3065-3074`) keeps cooldowns. BACKLOG.md:499-500 (CMB-10) is still open. Medium fits: a known open design question, not yet ruled an exploit.
- **Where:** `mods/PLAYER/grug_abilities/init.lua:3087-3105` (leave), `:3034-3063` (join), `kits_*.lua`/`scout.lua` cooldowns
- **What:** `on_leaveplayer` drops `cooldowns[name]`, `charges[name]`, `cast_intervals`, `cast_clock`, `mana` and `rage`; `on_joinplayer` calls `refill_mana`. A player who reconnects therefore comes back with every skill ready and a full mana bar. A death keeps the cooldowns (only the action clock and the cast intervals go, as classes.md "Control execution" says), so a relog is strictly better than dying. This hits the long timers hardest: Sprint (300 s, scout.md says "the five-minute cooldown remains its limit"), Unbroken, Ruination, Fire Rain, Winter Field, Haven, Final Word, Arrowfall, Close Dance (60 s each).
- **Evidence:** `init.lua:3092-3097` `mana[name] = nil ... cooldowns[name] = nil ... charges[name] = nil`; `init.lua:3053` `refill_mana(player)`; `scout.lua:334` `cooldown = 300`. classes.md:155-156 decides only that *resources* are runtime state; it says nothing about cooldowns. BACKLOG.md:499-500 (CMB-10) already asks the question "should long cooldowns and mana survive a relog?"; it is still open.
- **Proposal:** Keep the cooldown and charge records for a short grace period after leave (a table keyed by name with the absolute `get_us_time` expiry; `get_us_time` is monotonic per process, so a server restart clears it anyway, which is acceptable). Restore them in `on_joinplayer` and hand them to `cooldown_hud.track` again. If mana should also survive, store the current value in the same grace record. Nothing else changes: death and respawn behaviour stays as it is. This needs the CMB-10 ruling first.
- **Effort:** S · **Risk:** low · **Upgrade class (guess):** compatible
- **Confidence:** high

### C2-02 | Medium | perf | The 0.05 s input/attack pass reads the wielded item 3 times and checks unlock twice per player per step, even for idle players

- **Verdict:** CONFIRMED — `SWING_STEP = 0.05` (`init.lua:2932`) is below the engine default `dedicated_server_step` 0.09 (`reference_projects/luanti/src/defaultsettings.cpp:495`), so the pass runs every step for all players (`init.lua:2957-2972`). `input.step` evaluates `allowed()` (`input.lua:588`) before the idle return (`:623`). Engine now checked: `core.check_player_privs` (`builtin/game/misc.lua:17-26`) calls `core.get_player_privs` → `Server::getPlayerEffectivePrivs` (`src/server.cpp:3445-3449`) → the Lua auth handler's `get_auth` → `core_auth.read` (`builtin/game/auth.lua:10-12`) → `AuthDatabaseSQLite3::getAuth` (`src/database/database-sqlite3.cpp:707-722`, two prepared SQLite queries) plus two table copies; no mod registers its own auth handler. So each idle player costs an auth-database read per step, which makes the privilege check the most expensive item here. Nuance: the `is_unlocked` calls happen only when the wielded item is an ability item; the wielded-item copies and the privilege check happen for every player.
- **Where:** `init.lua:2957-2972` (globalstep), `input.lua:567-631` (`step`), `input.lua:68-78` (`allowed`, `selected`), `init.lua:1547-1551` (`selected_swing_def`), `init.lua:3138/3147` (`api.selected`)
- **What:** The accumulator threshold is 0.05 s, below the 0.09 s server step, so the pass runs on every engine step for every connected player in one step. For each player it does the following:
  - `input.step` calls `get_player_control()`, `get_wielded_item():get_name()` (line 576) and then `selected()`, which runs `api.selected` → a second `get_wielded_item()` and `is_unlocked`.
  - `is_unlocked` calls `grug_classes.get_class` → `player:get_meta():get_string`, plus `talent_rank` and `replacement`.
  - `allowed()` calls `core.check_player_privs` (an auth-database read in the engine, see the verdict), `is_stunned`, `player_has_live_mount` and the creation-stasis check.
  - Back in init.lua, `selected_swing_def` does a third `get_wielded_item()` and a second `is_unlocked`.

  All of this runs before input.lua's idle early return (line 623). Every 0.15 s the same step also runs `crosshair.update`, which does a fourth `api.selected` (another wielded-item copy), a third `is_unlocked`, a hand ray and usually a skill ray, again for all players in one step.
- **Evidence:** Callers per step: `init.lua:2966-2970`. Each `get_wielded_item()` returns a fresh ItemStack userdata. At 100 players and about 11 steps/s this is about 3,300 ItemStack copies, up to 2,200 `is_unlocked` (each with a meta read) and 1,100 privilege checks (each an auth-database read) per second at idle.
- **Proposal:** Read the wielded name and the selected def once per player per pass in the globalstep, then pass them to `input.step` (it already accepts a second argument) and to `crosshair.update`. `selected_swing_def` and `crosshair`'s `api.selected` would reuse them. In `step`, test the cheap "no button, nothing pending/waiting/mode, not cancelled" idle case before `allowed()`. When idle, `cancel` only latches a flag that line 618 clears in the same pass anyway, and `end_food_hold` is a no-op. Behaviour must stay identical for a held or pending press. Cache the `interact` privilege per player (refresh on `register_on_priv_grant`/`revoke`) or at least move it behind the idle test. Optionally cache the class id per player: the class can never change (skill_trees §3.10), so it is set once at `on_class_chosen`.
- **Effort:** M · **Risk:** medium · **Upgrade class (guess):** compatible
- **Measure:** unmeasured. Use 100 stand-in players idle and 100 holding LMB at a mob (any seed, the starter town), and compare the globalstep time of `grug_abilities` (profiler `--profiler` mod section, or `core.get_us_time` around the closure) before and after.
- **Confidence:** high

### C2-03 | Medium | perf | The 0.5 s regen/HUD pass handles every player in one step and recomputes max mana up to three times per player; every HUD draw calls `get_properties()`

- **Verdict:** CONFIRMED — `init.lua:2986-3028` loops all connected players; max mana at `:2998`, in `mana_regen_rate` (`:160`, in combat) and in `hud_state` (`:435`) via `hud_update(player, true)`; `hud_update` reads `get_properties()` (`:498`); `spend` always calls `hud_update` (`:256`). `get_max_mana` rebuilds `get_pool_breakdown` each time (`grug_classes/stats.lua:51-95`, `get_class` is a meta read at `grug_classes/init.lua:41-43`). AGENTS.md:312-314 states the one-step rule.
- **Where:** `init.lua:2986-3028` (pass), `init.lua:488-520` (`hud_update`), `init.lua:430-440` (`hud_state`), `init.lua:151-165` (`mana_regen_rate`), `init.lua:242-258` (`spend`)
- **What:** The pass visits every connected player at once, which breaks AGENTS.md "No pass handles every player or zone in one step". For a mana player it calls `grug_classes.get_max_mana` at line 2998, again inside `mana_regen_rate` when in combat (line 160), and again in `hud_update` → `hud_state` (line 435). Each call rebuilds `get_pool_breakdown`: `get_class` (a meta read), the level, `status_modifier_sum` over the sorted status list, and a new result table. `resource_of` (another meta read) runs twice as well. `hud_update(player, true)` also calls `player:get_properties()` (a full property table) per player per pass. Outside the pass, `hud_update` runs on every hp change, every `add_rage` and every `spend`. `spend` redraws even for a free cast with an empty cost (`init.lua:256`), so Fiery Spark, Smite and Loose each pay a `get_properties` and a max-mana rebuild per shot.
- **Evidence:** `init.lua:2994-3026`; `stats.lua:89-95` and `51-82` (grug_classes) for the max-mana cost. Every input to max mana already has a hook in this very file that calls `clamp_mana`: equipment change `init.lua:2409`, talents `:2767`, status modifiers `:2777`, level `:3115`, class `:2755`.
- **Proposal:** Cache `max_mana[name]` (and the class resource) in the existing `clamp_mana` path and at join, and read the cache in the regen pass, `hud_state` and `mana_regen_rate`. Cache `hp_max`/`breath_max` the same way, or read them only in the authoritative pass. Make `spend` skip `hud_update` when the cost table is empty. Spread the 0.5 s pass over slots (for example name-hash modulo 5 at 0.1 s), keeping `elapsed` per player so the regen sums stay identical.
- **Effort:** M · **Risk:** low · **Upgrade class (guess):** compatible
- **Measure:** unmeasured. Use 100 stand-in Mages in combat, and compare the profiler time of the 0.5 s closure and calls of `get_pool_breakdown` per second before and after.
- **Confidence:** high

### C2-07 | Low | edge | A stun resets the weapon clock, so the first swing after a stun is immediate
